# P2-07 科室工作台设计与验收边界

本轮实现已形成可审查候选；持久升级和最终审查结果另见验收索引与 ignored handoff。批准基线为 bb3e350；接口、真实 HTTP、数据库角色及浏览器为测试边界。

## 已确认范围

独立 `/admin/vnext/departments` 入口；复用 React/Vite、现有字段和 Owner。服务端私有部分草稿，提交与 Owner staging 同事务。CORE 维护和文件导入闭环，ORG05/ORG06 FULL 保持 BLOCKED_DEPENDENCY。用户批准 PR、Codex review 修复循环及最终合并。

## 持久化与接口

草稿修订追加写入 `department_master.workspace_draft_revision`；数据库生成稳定 ID 和记录时间，密文绑定状态、内容和授权元数据。读取/保存检查原始身份和当前权限；预期修订防止覆盖。工作台不新增审批事实，申请状态从现有候选、批准和提交推导。

有限草稿类型为科室、层级、映射、标识、演化、生命周期和影响处置。部分 schema 放宽字段存在性，保留类型和 closed 输入。提交执行完整对应 Owner schema，固定请求恢复，失败整体回滚。

浏览器只缓存保存请求 UUID 或提交的 ID／预期版本／requestId；来源行和附件均由服务端密文恢复。网络失败、提交已接受后的读取失败及文件接收后的读取失败保留原恢复标识；读取准确当前状态后才解除锁定。部分草稿不授予平台审批或服务回执权限。

CORE 层级工作簿由现有有界解析 worker 执行 ORG05/ORG06 两表检查，继续使用 1 MiB、2 秒及 64 MiB 边界。原文件保存在私有密文草稿；提交重新解析并校对原 payload。文件草稿来源字段只读，修改重新上传；手工草稿仍支持完整整树编辑。发布和关闭分别绑定原候选的准确请求、摘要及独立审核。

层级列表、候选、历史和准确版本对比使用原 Hierarchy Owner；整个期间查询只返回一份覆盖请求的冻结发布快照。更晚的部分发布不通过旧树补齐，原版本和摘要保持不变。当前关闭状态与冻结发布事实分别返回。

新建视图的 SUBMITTED 草稿授权元数据绑定实际生成的 viewId；撤销准确视图 READ 后，私有读取、原保存请求恢复和已接受提交重放均拒绝，原来源内容不改写。候选历史状态和批准人按实际 approved_at／applied_at 与指定 R 比较。Catalog 的审批状态与影响提案证明通过其有限事务接口读取，Department 不直接访问 Catalog 表。

工作台装配多个 Owner 时共享两个 timestamp 解析族的有界连接池，每族最多 3 个连接；保持现有服务角色 8 个连接上限，保留 Catalog 原解析及领域 Owner 的微秒字符串。连接在 Kysely 初始化时分配，最后一个实际使用者关闭时释放，未使用的事务内 stage port 不创建连接租约。

## 阶段验收
