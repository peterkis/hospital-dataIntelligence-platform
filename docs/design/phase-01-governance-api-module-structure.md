## 1. 目标与边界

本文定义`apps/governance-api`内部源码组织和协作原则。目标不是套用固定分层模板，而是让每个治理能力形成一个具有深度的模块：调用方只需理解一个小型接口，就能获得完整的不变量、版本、权限、事务、审计和错误行为；维护者可以在模块内部改变实现而不扩散到调用方。

本文不一次性决定全部模块清单，也不创建源码。当前已经冻结`charge-catalog`、`price-list`、`price-resolution`和`release-distribution`四项深模块边界；消费者交付配置已经确定为独立治理对象，但其物理模块归属和私有执行组件位置尚未确认，且不进入Phase 01，不得据此预建新模块或未使用port。全部ABG门禁通过后，完整POC才为受控导出邻接薄切实现所需的最小配置治理与内部adapter；导入、身份授权和审计等其余能力仍需逐项决定哪些合并为一个深模块、哪些独立存在。

## 2. 统一术语

本设计使用以下工程术语：

- **模块**：具有一个外部接口和隐藏实现的治理能力单元。
- **接口**：调用者使用模块必须知道的全部内容，包括方法、输入输出、不变量、顺序、权限、错误和事务语义；不限于TypeScript `interface`关键字。
- **实现**：模块接口后面的状态机、规则、持久化、路由和内部协作。
- **seam**：可以替换行为而不修改调用点的位置；只有存在真实变化需求时才建立。
- **adapter**：位于seam并满足其接口的具体实现。
- **组合根**：唯一创建具体实现、注入依赖、建立事务作用域、注册Fastify路由及生命周期的位置。

这些是工程设计术语，不进入医院治理领域的`CONTEXT.md`。

## 3. 纵向组织方式

目标源码形态为：

```text
apps/governance-api/src/
├─ composition/
│  ├─ build-application.ts
│  ├─ build-request-scope.ts
│  └─ lifecycle.ts
├─ platform/
│  ├─ database/
│  ├─ request-context/
│  ├─ transaction/
│  └─ fastify/
└─ modules/
   └─ <capability>/
      ├─ index.ts
      ├─ implementation/
      ├─ adapters/
      └─ tests/
```

上图是责任示意，不要求每个模块机械创建相同子目录。小模块可以只有`index.ts`和少量实现文件；只有实现复杂度确实存在时才拆分内部目录。禁止在`src`根部建立跨所有治理能力的`controllers`、`services`、`repositories`、`models`或`utils`水平层。

每个模块的`index.ts`是唯一允许其他模块导入的入口。实现文件、数据库行类型、Fastify路由、内部状态及测试辅助均不得从该入口导出。

## 4. 模块深度和外部接口

一个模块只能有一个逻辑外部接口。接口可以由少量命令与查询方法组成，但不得把内部对象逐一暴露为大量CRUD类、仓储接口或过程步骤。

接口必须明确：

1. 接受的稳定身份、版本引用、命令或查询输入。
2. 调用主体、请求关联、幂等、院区范围及适用的业务时点。
3. 成功结果、版本、内容摘要及必要证据引用。
4. 稳定错误码、规则编号、失败关闭和并发冲突语义。
5. 是否要求既有事务作用域，以及提交后才能发生的动作。
6. 调用顺序、重复调用和重试语义。

接口不得暴露：

- `pg`连接、Kysely事务、SQL片段或数据库行类型。
- Fastify `Request`、`Reply`或HTTP状态对象。
- 内部状态机步骤、仓储对象、缓存或adapter。
- “先调用A，再从仓储取B，然后手工写审计”的内部过程。
- 允许调用者绕过权限、版本、不变量、审计或Outbox的低级写方法。

接口深度以调用者获得的行为杠杆衡量，不以实现文件数量或代码行数衡量。删除一个模块后，如果其复杂度只是原样散落到调用者，说明模块具有深度；如果删除后只少了一层转发，说明它是浅模块，应合并或重新设计。

## 5. 组合根

组合根承担且仅承担下列职责：

1. 创建PostgreSQL连接池、Kysely实例、Keycloak/OIDC适配、时钟和摘要器等当前具体实现；Phase 01不装配权威快照文件或对象存储实现。
2. 建立应用级和请求级上下文。
3. 将依赖注入模块实现，并把模块接口汇集为事务作用域应用上下文。
4. 注册模块拥有的Fastify路由adapter、Schema和生命周期钩子。
5. 启动及停止`release-distribution`内部派发器并处理提交后唤醒。
6. 为测试组合根替换明确允许的故障adapter，不向生产配置暴露测试入口。

模块不得访问全局可变容器、运行时服务定位器或通过字符串名称取得任意依赖。只有组合根知道具体实现类型；其他模块只知道被允许调用的接口。

Fastify路由属于对应治理模块的HTTP adapter，而不是全局controller层。路由只负责协议解析、身份上下文传递、调用模块接口及结果映射，不能重新实现领域规则。

## 6. 事务作用域应用上下文

跨模块原子操作必须共享同一PostgreSQL事务，同时避免把数据库事务对象扩散到模块接口。实现模型为：

```typescript
await transactionRunner.run(requestContext, async (modules) => {
  const decision = await modules.workflow.approve(command)
  const domainRelease = await modules.priceList.publishApproved(decision)
  const distribution = await modules.releaseDistribution.register(domainRelease)
  await modules.audit.recordRelease(domainRelease, distribution)
  return { domainRelease, distribution }
})
```

上述示例已经冻结“领域模块交付类型化内容投影、`release-distribution`生成快照制品”的责任方向，但不冻结具体TypeScript方法名、投影Schema字段或物理载荷结构。`transactionRunner`内部取得一个连接并建立Kysely事务，再创建与该事务绑定的模块实现集合；回调看到的是模块接口，不是连接、SQL或事务句柄。提交后的派发唤醒由事务运行器或组合根触发，不是回调内的网络动作。

事务规则如下：

1. 单模块命令默认由应用入口在一个事务作用域内执行。
2. 跨模块编排者只能调用作用域内模块接口；所有数据库写入使用同一连接和事务。
3. 模块不能自行提交、回滚或开启不受协调的嵌套事务。
4. 任一模块失败时，事务运行器回滚全部本地写入并返回稳定错误；调用者不能通过捕获后继续提交部分结果。
5. 发布、PostgreSQL `bytea`快照字节及元数据、兼容预检与独立投递登记、审计和Outbox继续满足同一事务原子性。
6. Outbox进程内唤醒、网络投递和其他提交后动作在成功提交后运行，不能进入事务回调。
7. 事务超时、取消、重试和数据库错误映射由事务运行器集中处理，但不得吞掉模块的领域错误。

请求上下文可以携带本地安全主体、请求ID、关联ID、幂等键和固定`Asia/Shanghai`本地日期时间；它不包含可由业务代码任意操作的数据库句柄。事务绑定采用显式对象、闭包或其他机制属于实现选择，但必须保持上述接口和证据语义。

## 7. 跨模块协作

跨模块协作遵循：

- 命令和需要当前权威结果的查询通过被调用模块接口直接执行。
- 跨模块引用使用稳定身份和已冻结版本引用，不传递对方内部实体对象。
- 一个模块不得直接读取、插入、更新或删除另一个模块拥有的表，也不得导入其内部数据库类型。
- 跨模块列表或报表优先通过明确查询接口或独立只读投影实现，不能在任意仓储中拼接跨模块表。
- 组合根解决装配顺序；模块之间不得形成循环源码依赖。
- 必须同步失败关闭的校验不能改为异步“最终再检查”。`release-distribution`内部Outbox只负责已登记发布事实的外部投递，不承担其他模块的本地事务内协作。

Phase 01默认使用直接、类型化的模块接口调用，不为形式统一引入通用命令总线、Mediator、内部事件总线或动态插件系统。未来如确有第二种调用adapter或独立替换需求，应以接口深度和真实变化点重新评审，而不是预先制造seam。

## 8. adapter与seam纪律

只有依赖确实变化或位于真实外部边界时才建立seam：

- Keycloak/OIDC和仿真消费者属于当前真实外部或远程依赖，可以通过小型内部接口隔离协议细节。未来若经新ADR启用外部快照对象存储，届时才建立所需adapter；Phase 01不得预建未使用的存储port。
- PostgreSQL持久化在Phase 01只有一个正式实现，不为使用内存仓储测试而给每张表创建repository接口；Kysely和SQL映射隐藏在拥有该行为的模块实现中。
- HTTP路由是治理模块接口的adapter；路由测试验证协议映射，模块测试验证行为，不复制两套业务实现。
- 测试故障点是测试组合根可替换的内部seam，不得扩大为生产接口。

一个seam只有一个adapter且没有已知变化需求时通常是无价值间接层。模块内部可以有私有seam支持复杂实现，但不能仅因测试需要就把它们暴露到模块外部接口。

## 9. 允许共享的技术能力

治理模块可以共享少量、明确命名且没有业务主权的技术能力，例如：

- 请求及关联上下文。
- `LocalDateTime`、Decimal、内容摘要和稳定标识的无损基础实现。
- 事务运行器、数据库连接基础设施和统一错误包络映射。
- 日志、安全脱敏和可观测性基础设施。

这些能力必须位于精确命名的`platform`子模块中，不能形成`common`、`shared`、`helpers`或`utils`倾倒目录。治理对象规则、状态机、Owner判定、权限、版本、价格解析和发布语义不得进入共享技术模块。

禁止`BaseService`、`BaseRepository`、`BaseController`、通用CRUD框架和通过继承强制所有模块同形。共享行为应由真正有深度的模块接口提供，而不是由通用基类扩散隐式约束。

## 10. 测试策略

模块接口是主要测试面：

1. 接口测试验证命令、查询、不变量、错误、权限、版本、事务和可观察副作用。
2. 涉及持久化的接口测试使用Testcontainers中的真实PostgreSQL 18.4，不以SQLite、内存repository或PGLite替代正式门禁。
3. 纯计算规则可以在模块内部建立快速测试，但这些测试不能成为调用者依赖内部结构的理由。
4. Fastify `inject()`测试验证HTTP adapter、TypeBox校验、身份上下文和错误映射。
5. REST验收继续通过冻结OpenAPI生成客户端，不能直接调用模块接口代替外部场景。
6. 自动化依赖检查阻断跨模块内部路径导入、循环依赖、对方表访问、横向根目录和通用业务基类。
7. 模块内部重构不应迫使接口测试改变；若测试大量依赖实现细节，应重新评审接口深度。

同一行为从浅层类逐步合并进深模块后，应删除被新接口测试完全取代的重复测试，避免一项行为由多层脆弱测试同时维护。

## 11. 数据所有权与迁移

原生SQL迁移仍统一位于根`db/migrations`，不移动到各模块npm包。每项表、约束、索引和迁移必须登记逻辑拥有模块；集中物理目录不等于全应用可以任意访问所有表。

模块实现只能通过自身持久化代码访问所拥有表。确需跨模块原子协调时调用模块接口并共享事务作用域；确需跨模块查询时建立明确接口或只读投影。数据库角色、静态SQL扫描、测试或代码检查至少有一种可执行机制证明模块不能静默写入他模块表。

### 11.1 版本与生命周期所有权

版本和生命周期不是可以从治理对象抽离的通用技术能力：

| 能力 | 拥有模块 | 其他模块允许做什么 |
|---|---|---|
| 收费项目稳定身份、内容版本、替代/拆分/合并关系及业务生命周期 | `charge-catalog` | 通过接口校验或冻结明确的收费项目版本引用 |
| 价表稳定身份、完整发布版本、价格条目及业务生命周期 | `price-list` | 按双时点取得不可变已发布价格解析视图或冻结发布版本引用；不得由调用者读取草稿或表 |
| 固定两级价格解析、通用/专用判定、规则执行、舍入和解析证据 | `price-resolution` | 提交解析命令或查询既有证据；不得由调用者写入解析证据表或改变价表 |
| 审批模板、变更请求、前置确认和审批动作状态 | 工作流模块 | 提交领域变更摘要并取得不可伪造的审批决定引用 |
| 通用发布包络与成员、快照制品及元数据、Outbox事件、消费者订阅、投递、尝试、平台侧检查点与回执 | `release-distribution` | 领域模块只能通过接口传入冻结的类型化内容投影；调用者可以查询快照/变化/投递及提交回执，但不得改变领域版本或直接写入分发存储 |
| 只追加操作、前后摘要和完整性链 | 审计能力 | 追加或查询证据，不重建领域当前状态 |

`governance_release`只表达“一次治理对象发布”的通用包络、序号和关联证据；它不是所有内容版本的超类，也不拥有收费项目或价表的状态机。`charge_item_version`和`price_list_release`继续由各自模块解释、校验和演进，`release-distribution`不能直接创建或修改这些领域记录。

工作流最终批准只产生审批决定，不能直接把领域草稿改成已发布；领域模块在同一事务作用域内验证决定、执行自身状态转换、构造冻结的类型化发布内容投影，再调用`release-distribution`和审计接口。发布失败时整个本地事务回滚，不留下“工作流已批准但领域版本半发布”的终态。

未来人员主数据、科室主数据、标准值域或数据元进入工程时，同样由对应治理对象模块拥有身份、版本和生命周期；不得复用通用`VersionService`、`BaseVersion`、`VersionedRepository`或可配置状态机取代已确认的对象语义。无时区本地日期时间、流内序号和内容摘要等无业务主权的值实现可以共享，但不能包含领域状态转换。

### 11.2 `price-list`到`price-resolution`的只读依赖

`price-resolution`是独立深模块，但与`price-list`保持同进程模块接口调用，不形成HTTP回环或微服务。依赖方向固定为`price-resolution -> price-list`公开接口，不存在反向源码依赖。

`price-list`公开的是概念上的`PublishedPriceResolutionView`，具体TypeScript方法名和物理字段留待实现设计。该视图必须：

1. 按价表稳定身份、`service_occurred_at`和`record_as_of`确定唯一权威的已发布价表版本；零个或多个候选时返回稳定、可留证的失败结果。
2. 冻结发布版本ID与内容摘要、业务和记录区间、发布及暂停状态、目标稳定身份与冻结版本，以及相关价格条目ID、内容摘要、范围、模式、时间和计价规则版本引用。
3. 可以从本模块不可变发布数据收集与请求目标及时间相关的候选集合，但不能替`price-resolution`决定院区或全院命中、通用或专用模式、冲突回退、规则结果及最终金额。
4. 不暴露草稿、Kysely/`pg`类型、数据库行、SQL或可用于写回价表的句柄。

`price-resolution`取得该视图后，独占输入规范化、院区到全院固定两级检查、每层通用/专用互斥及唯一命中、固定价或已发布计价规则执行、Decimal计算、舍入和失败关闭。它拥有`price_resolution`、`price_resolution_step`和`price_resolution_result`，并在同一解析事务中追加请求摘要、视图及候选摘要、有序步骤、引用版本和结果摘要。后续价表发布不修改历史解析证据；重放时使用证据冻结的发布视图身份与摘要，而不是重新读取“当前最新版”。

若`price-list`无法给出唯一发布版本、视图摘要不一致、候选集合冲突、引用版本暂停或规则执行失败，`price-resolution`必须产生相应稳定失败状态并保存已完成的证据，不得改查草稿、跳过院区冲突回退到全院，也不得由路由层临时补齐算法。

### 11.3 `release-distribution`统一发布登记与提交后投递

`release-distribution`是一个深模块和一个逻辑外部接口。它统一拥有`governance_release`、`release_member`、包含权威`bytea`制品字节的`release_snapshot`、`outbox_event`、`consumer_subscription`、`outbox_delivery`、`outbox_delivery_attempt`以及平台侧`consumer_checkpoint`、`consumer_receipt`。物理迁移仍集中在`db/migrations`，但其他模块不得直接查询或写入这些表。

接口应以少量高杠杆操作覆盖：

1. 在调用方事务作用域内接收领域模块已经固化、经批准且完成语义校验的类型化内容投影，对当时适用的活动订阅版本执行本地兼容性预检，登记不可变发布、暂停、失效或补偿事实，并返回冻结的通用发布、快照、事件和逐订阅预检引用。
2. 版本化管理消费者订阅及其精确投影支持声明，并通过稳定游标查询已发布快照、变化、兼容结果和按消费者隔离的投递状态。
3. 接收并追加消费者接收、校验和应用回执，执行水位及缺口不变量。
4. 在消费者发布新的支持声明后，对不兼容或待人工处置投递执行受控重放命令，重新校验原事件与原快照，只追加新结果和尝试，不覆盖旧状态证据。

具体方法名、命令类型和物理字段留待实现设计；接口不得暴露租约认领、轮询批次、SQL、数据库行或内部状态机步骤。租约认领、重试计算、顺序阻断、网络adapter和投递投影更新属于模块实现及其私有seam。

模块内部必须保持以下阶段隔离：

| 阶段 | 事务边界 | 允许行为 | 禁止行为 |
|---|---|---|---|
| 发布登记 | 调用领域发布的同一本地事务 | 接收冻结投影，生成包络、规范字节及摘要，把最终字节原样写入PostgreSQL `bytea`，对冻结活动订阅版本执行本地兼容性预检，并原子登记快照元数据、成员、逐订阅结果、审计和Outbox事实；不兼容结果只产生被阻断投递和影响事项 | 回查领域表、延迟取数、调用消费者、写文件/S3或暂存提升、把不兼容结果当作发布失败、自行提交、修改领域版本或审计链 |
| 提交后激活 | 无业务事务 | 发送进程内唤醒提示；数据库轮询仍为恢复权威 | 把唤醒当唯一可靠队列 |
| 投递认领 | 独立短事务 | 只筛选契约兼容且已到期的记录，使用`FOR UPDATE SKIP LOCKED`写有限租约并提交 | 认领`BLOCKED_INCOMPATIBLE`投递、跨网络等待持锁 |
| 网络发送 | 事务外 | 至少一次发送正式事件包络 | 声称恰好一次或把发送等同消费者应用 |
| 结果持久化 | 新短事务 | 条件校验租约、追加尝试、更新本消费者投递投影 | 覆盖旧尝试或其他消费者状态 |
| 回执与检查点 | 独立事务 | 追加回执、验证缺口、单调推进平台侧观察水位 | 代替消费者自身幂等状态或跳过缺口 |

统一为一个模块不允许把这些阶段合成一个长事务，也不允许把内部派发器暴露为第二个模块接口。领域模块仍拥有内容版本和生命周期；工作流拥有审批决定；审计模块拥有只追加完整性链；仿真消费者在治理应用外拥有自己的幂等应用状态。`release-distribution`只把不可变领域事实变成可恢复、可查询、可留证的分发事实。

### 11.4 领域内容投影到快照制品的seam

该seam传递的是冻结、类型化且已完整物化的值，而不是数据库访问能力：

1. `charge-catalog`、`price-list`及未来人员、科室、值域和数据元模块分别从自己拥有的权威状态构造发布内容投影，并在跨越seam前完成字段、引用、状态和集合完整性的领域校验。
2. 投影冻结稳定身份、明确内容版本及必要引用；可以携带领域版本已有摘要作为证据，但不得携带数据库行、SQL、Kysely/`pg`类型、repository、事务句柄、延迟加载器或稍后回查“当前数据”的回调。
3. `release-distribution`负责通用包络、确定性规范序列化、投影载荷摘要、完整制品摘要、不可变存储、快照元数据和Outbox；它只理解通用制品不变量，不解释、推断、补齐或迁移领域字段。
4. 领域模块不得写`release_snapshot`、快照存储或Outbox，也不得把自己生成的任意JSON、REST DTO或最终字节当成权威发布快照；`release-distribution`不得查询任何领域模块表来补全投影。
5. 相同冻结投影、相同通用包络输入、算法和序列化规则必须产生逐字节相同的投影载荷、快照制品及双摘要。具体TypeScript值类型和物理列名不由本节锁定，但Phase 01制品介质固定为`release_snapshot`内非空PostgreSQL `bytea`；投影Schema主权及版本规则见下一节，摘要作用域见11.9节，存储边界见11.10节。

该接口仍是`release-distribution`唯一外部接口的一部分，不另建“snapshot-builder”浅模块。领域投影构造可以是领域模块内部实现及测试面，但不能成为供其他模块绕过领域接口的共享数据装配层。

### 11.5 领域投影Schema主权与单一外部契约链

每个领域模块通过自己的唯一`index.ts`公开其投影契约，这是该模块Interface中调用者必须知道的一部分，而不是后端内部数据库类型泄漏：

1. 领域模块拥有稳定`projection_type`、投影字段及解释、可执行TypeBox Schema和不可变`projection_schema_version`；结构、约束或字段解释发生变化都形成新版本，已用于发布的版本不得原位修改或删除。
2. 投影跨越seam时冻结`projection_type`、`projection_schema_version`、`projection_schema_digest`及摘要算法标识。版本标识格式留待实施选择，不得仅凭数值大小或SemVer外观推断兼容性。
3. 组合根从各已纳入领域模块的公开接口取得Schema，在Fastify路由注册时确定性组合快照和变化响应的TypeBox Schema；冻结OpenAPI 3.1仍是管理界面、仿真消费者和测试生成客户端的唯一外部输入。
4. `release-distribution`只核对投影三元契约身份与组合根登记的不可变定义一致，并把该身份写入包络、事件和查询结果；不得定义领域字段、替领域模块选择版本、隐式迁移、自动升降级或重新解释旧内容。
5. 只要快照仍引用某投影Schema版本，其可执行定义、Schema摘要及对应冻结OpenAPI证据必须保持可追溯。TypeBox派生的Schema清单或客户端可以作为产物保存，但不得反向成为可编辑权威。

这不新增集中式`projection-schema`模块或动态插件系统。组合根只装配已知模块提供的契约，`release-distribution`保持通用；消费者如何显式支持这些契约见下一节。

### 11.6 消费者精确支持声明与不兼容投递隔离

消费者兼容性仍封装在`release-distribution`同一个深模块及逻辑Interface内，不建立独立`compatibility`模块、转换服务或消费者探测器：

1. 每个订阅稳定身份通过不可变订阅版本声明精确支持的`projection_type + projection_schema_version`集合；每个组合必须解析到组合根登记的唯一Schema摘要。`latest`、通配符、版本范围、SemVer推断和按字段试读均不是合法声明。
2. 发布提交前，模块使用候选投影契约与当时适用的活动订阅版本执行纯本地、确定性的逐订阅预检，并冻结订阅版本、契约身份、规则版本和`SUPPORTED`或`UNSUPPORTED`结果；预检不得调用消费者或依赖其可用性。
3. `SUPPORTED`投递进入既有待投递、租约、重试和回执状态机。`UNSUPPORTED`不阻断或回滚领域发布，而是使该消费者投递进入`BLOCKED_INCOMPATIBLE`并创建影响事项；该状态不具备租约资格，不产生网络发送或投递尝试，也不推进平台检查点及消费者水位。
4. 兼容消费者继续独立投递。一个消费者的不兼容结果不得写回Outbox事件的全局状态，也不得阻止其他订阅。
5. 消费者升级必须形成新的订阅版本。受控重放对原事件和原不可变快照使用新订阅版本重新预检；通过后才允许原投递进入待投递状态，并追加重放决定和后续尝试。原不兼容结果、影响事项及旧订阅版本继续保留。
6. `release-distribution`不得转换载荷、自动降级、迁移Schema、重解释字段或私自选择另一投影版本；同一领域发布在Phase 01只存在下一节定义的一个规范投影快照。

### 11.7 一发布一规范投影快照及扩展接缝

Phase 01把领域发布事实和快照制品建模为两个相邻但不同的身份，同时严格执行一对一基数：

1. 领域模块对一次发布只构造一个规范内容投影，并冻结唯一`projection_type + projection_schema_version + projection_schema_digest`；`release-distribution`只据此生成一个`CANONICAL`权威快照。全部消费者预检、事件、查询和重放引用同一制品。
2. 发布登记必须返回并留存相互不同的发布身份和快照制品身份；不能合并两种ID、把快照ID当发布ID、把“当前快照指针”覆盖旧制品，或在规范快照中写入消费者身份。
3. 同一发布登记第二个快照、并行Schema版本、消费者专用快照、降级副本或其他内容变体必须失败关闭；不得通过再次调用内部步骤、绕过接口写表或复制`governance_release`来适配消费者。
4. 投影Schema升级由领域模块发起新的显式发布，即使其冻结的领域内容版本及成员集合未变化，也必须产生新的发布序号、契约身份、快照制品、投影载荷摘要、完整制品摘要、审批和预检证据；旧发布和旧快照永不重打包。
5. 长期扩展性只由发布事实与制品身份分离这一既有seam保证。Phase 01不新增投影注册器、转换器、变体路由器、消费者选择器、专用快照接口或未被当前用例调用的port。
6. 未来多投影版本或专用`release_snapshot`仍必须经新ADR定义制品角色、受众、路由、退役和语义等价门禁，并沿同一领域模块投影所有权与`release-distribution`制品封装边界扩展；ADR-0096允许的厂商专用派生交付制品位于初始化交付作业，不是`release_snapshot`，不得成为第二领域真相或被用于规避本节基数。

### 11.8 投影Schema升级责任与证据边界

Schema升级不改变既有模块所有权，也不建立第五个契约治理模块：

1. 所属领域模块继续拥有投影字段、语义、TypeBox Schema和版本；领域Owner通过工作流动作确认新Schema与领域含义一致。平台契约Owner只确认对外结构、契约身份和证据完整性，不能直接编辑领域Schema。
2. 工作流模块冻结`PROJECTION_SCHEMA_UPGRADE`高风险变更分类、旧/新契约身份、领域内容与成员摘要、审批模板及职责分离策略，并拥有领域语义确认、平台契约终审和四类强制证据的流程状态。
3. 终审前必须引用TypeBox/OpenAPI差异、依据活动订阅精确支持版本生成的兼容矩阵、冻结契约生成客户端的仿真消费验证运行和影响分析。缺一项即失败关闭；验证运行不是发布时消费者网络探测。
4. 纯契约升级且领域内容、成员、规则和生命周期均未变化时，模板可以允许提交人兼任平台契约终审人。同一主体仍须分别通过提交、领域语义确认和平台契约确认的授权检查并追加不同动作；若任一领域事实变化，工作流改用普通职责分离策略。
5. 消费者Owner只经版本化订阅接口声明支持与迁移准备，不进入审批模板。`UNSUPPORTED`仍只形成对应`BLOCKED_INCOMPATIBLE`投递，不具备否决领域发布的转换路径。
6. `release-distribution`只接受领域模块传入的批准决定及证据引用，核验引用完整性后生成唯一规范快照；它不计算OpenAPI差异、不审批Schema、不解释影响分析，也不因消费者不兼容拒绝发布。

### 11.9 投影载荷与完整快照制品双摘要

双摘要是`release-distribution`内部制品职责的一部分，不形成新模块或共享领域服务：

1. 模块在冻结`serialization_profile_version`下先形成投影载荷规范字节并计算`projection_payload_digest`，其范围严格止于投影载荷；通用包络或运维状态变化不得改变该摘要。
2. 模块随后形成最终落盘的冻结通用包络与投影载荷完整字节并计算`snapshot_artifact_digest`。该摘要保存在快照元数据、事件和查询结果中，不嵌入自身覆盖的制品字节。
3. PostgreSQL表名、列名、物理行位置、投递状态、尝试、回执、审计链状态及可变运维元数据不属于快照制品字节，也不进入任一摘要。
4. 两类摘要分别冻结算法标识并共同冻结序列化规则版本；Phase 01初始算法为SHA-256。历史核验必须使用原快照记录的算法和规则，禁止以当前实现重算、覆盖或补写。
5. 领域模块已有的版本摘要或成员集合摘要继续证明领域内容是否相同。跨Schema时不得依据投影载荷或完整制品摘要推断领域语义等价；结构变化可以在领域证据相同时产生不同的载荷摘要。
6. 快照和事件外部契约明确命名并同时携带两类摘要及算法，不使用含义模糊的单一`content_hash`；消费者先核验完整制品摘要，再按冻结包络取得投影载荷并核验载荷摘要。

不得新增`digest`、`hashing`或同义模块、服务、workspace或共享领域抽象。无业务主权的SHA-256字节函数可以作为模块内部基础实现复用，但不得拥有快照、领域内容或验证流程状态。

### 11.10 PostgreSQL事务内权威快照存储

Phase 01把权威快照存储作为`release-distribution`现有PostgreSQL持久化职责，不形成新模块或外部资源边界：

1. 每个唯一`CANONICAL`快照的最终制品字节以非空`bytea`保存在`release_snapshot`；该逻辑值必须与`snapshot_artifact_digest`覆盖的字节逐字节一致。PostgreSQL内部TOAST或物理压缩不改变制品契约。
2. 快照字节、媒体类型、字节数、双摘要及算法、发布事实、成员、兼容预检、独立投递登记、审计和Outbox全部使用领域发布的同一连接与事务；任一故障全部回滚，不存在数据库已发布而制品仍待提升的状态。
3. 模块外只提供按稳定快照身份授权查询元数据和下载字节的逻辑能力。事件携带快照ID或等价稳定获取引用，不携带完整正文；REST契约不得暴露数据库表、列、连接或物理位置。
4. 业务用户、治理角色、管理界面、仿真消费者及外部测试均不得直接读取治理数据库；应用服务账号继续使用最小权限访问自己拥有的表。
5. Phase 01不使用本地/共享文件、S3兼容对象存储、数据库与外部存储双写、暂存提升、跨资源补偿，也不预建`SnapshotStore`、对象存储adapter或第二个存储workspace。
6. 未来迁移对象存储必须另立ADR和追加迁移，保持快照ID、下载契约、历史字节及双摘要不变；当前合成POC容量护栏见11.11，不得推导为未来存储介质或全院容量结论。

### 11.11 Phase 01单快照容量护栏

容量校验继续封装在`release-distribution`内部，不形成通用容量模块或未来生产配置承诺：

1. 模块在最终规范制品字节形成后计算`artifact_byte_length`，该值必须与即将写入`artifact_bytes`并由`snapshot_artifact_digest`覆盖的字节序列长度完全相同。
2. Phase 01合成POC允许`artifact_byte_length <= 16,777,216`；大于该值返回`SNAPSHOT_ARTIFACT_TOO_LARGE`并使发布事务不形成已发布结果。边界测试必须覆盖恰好16,777,216字节成功和16,777,217字节失败。
3. PostgreSQL TOAST、HTTP内容编码和其他物理压缩不改变计量值；领域模块、路由和消费者不得裁剪、拆分、压缩或改换序列化规避上限，也不存在文件或对象存储回退。
4. 超限后不得形成发布事实、快照、投递登记、Outbox或消费水位推进；失败尝试沿既有失败审计路径留痕，不得写成成功发布。
5. 16 MiB只限制当前合成POC的事务、内存、备份和故障测试范围，不是全院初始化、生产运行、性能SLA或招标参数，不能成为全平台永久常量。
6. 未来全院初始化或生产设计必须使用代表性规模、字段分布、版本保留、并发、WAL、备份恢复、下载和消费者恢复数据完成容量验证，再以新ADR确认上限、分片或存储策略。

### 11.12 三种交付模式的统一闭环接缝

`SNAPSHOT_PULL`、`MANAGED_EXPORT_HANDOFF`和`RECORD_PUSH`继续属于`release-distribution`同一深模块的交付责任，不建立新的`initialization-service`、`export-service`、`push-service`或独立workspace。模块统一拥有初始化作业、模式动作、逐记录进度、回执、对账和检查点的通用不变量；具体下载、文件生成或第三方HTTP调用只是模块内部adapter，只有对应模式进入已确认实施范围时才建立，不得为长期设想预建未使用port。

初始化交付作业必须与日常增量投递分别建模：

1. 初始化作业冻结消费者及订阅版本、来源发布、唯一规范快照和一种交付模式；受控导出还冻结精确重试策略、格式和算法版本。增量继续由`outbox_event`、`outbox_delivery`及其尝试承载。
2. 三种模式共同读取或派生自同一固定规范快照，不允许adapter查询领域当前表、创建新的领域版本、治理发布或规范快照变体。
3. 消费者交付配置是独立版本化治理对象，每版冻结目标消费者、用途、精确来源`projection_type + projection_schema_version`、交付契约、模板、映射和派生交付格式版本、CSV列序/字段表示/全序记录规则、声明式转换计划及固定测试向量；来源领域Owner强制语义前置确认，集成交付Owner单一终审。只有验证通过且已批准的版本可进入作业。
4. 默认计划只能组合字段选择、排序、重命名、确定格式/类型转换、空值/默认值策略、常量元数据和已发布代码映射版本引用。过滤、拆分、合并、聚合、计算字段和一对多展开默认禁止，启用前须有独立高风险能力审批及固定测试向量；当前没有任何具体高风险能力获准。
5. 任意脚本、SQL、网络调用和运行时当前状态查询绝对禁止，不建立可由高风险审批打开的脚本、查询或网络扩展seam，也不建立通用ETL平台。
6. 配置终审前必须对精确来源Schema和固定样例向量验证全部操作并只追加保存逐项证据。未知能力、字段/类型不匹配、映射无效或结果不一致失败关闭。
7. 使用厂商专用转换的作业必须同时冻结精确消费者交付配置版本，且固定规范快照的投影契约必须与之完全匹配。执行、重试或恢复不得解析`latest`或自动换用配置新版。
8. 完整POC每个成功的`MANAGED_EXPORT_HANDOFF`作业只形成一个独立身份、不可变且非权威的确定性无压缩ZIP；`release-distribution`只能执行作业冻结且验证通过的声明式计划和格式版本，并封装作业、制品身份、外置完整ZIP摘要、内置清单、下载/交接证据、回执和对账状态，不得编辑配置或映射、推断领域含义或查询当前领域表，也不得将制品写成`release_snapshot`或复用规范双摘要。
9. 固定规范快照中的任一记录发生确定性转换错误时，`release-distribution`必须使整个导出作业进入终态失败并保证零个完成制品；临时或部分字节不能下载、交接、回执、通过对账或推进检查点，也不能提供跳过错误、静默丢弃或“成功记录＋错误清单”的恢复分支。
10. 转换失败作业必须只追加保存作业级及行级错误，关联固定来源、配置版本、成员身份或作业内序号、字段或操作、稳定错误码和安全诊断摘要。修正来源、映射或配置必须建立相应新发布或版本及新作业，原失败作业不可改换来源或续写；导入行级部分成功语义不受影响。
11. 冻结重试策略必须明确稳定技术错误分类、可自动重试的瞬时分类、有限自动尝试额度和退避规则；未知、未分类或明确不可重试的技术错误不得自动重试，具体次数和时长属于版本化配置而不是硬编码领域常量。
12. 每次受控导出执行以正数且不复用的`attempt_no`追加证据，并从冻结的来源、快照、消费者、订阅、配置、重试策略、格式和算法完整重建；不得按成员或部分字节续跑，失败临时字节不得取得制品身份。
13. 自动额度耗尽或遇到未知技术错误时，作业进入`TECHNICAL_ATTENTION_REQUIRED`并生成影响事项，保持零制品。对象级授权人员可在冻结输入不变时发起一次受控重试，追加新尝试但不重置自动额度；再次失败重新待处置，任何输入变化则必须新建作业。
14. ZIP内`manifest.json`冻结来源发布/快照及快照摘要、目标消费者和订阅、精确消费者交付配置及其交付契约/模板/映射/格式/算法版本、CSV列和排序规则身份、记录数量、`records.csv`字节数/SHA-256和非权威声明；完整ZIP摘要、作业/尝试/制品身份、时间、交接状态及存储位置保存在制品外部。配置、内容、格式、模板或映射变化必须形成新配置版本、新作业与新制品，既有证据不覆盖或自动迁移。
15. `RECORD_PUSH`的成员进度和尝试留在初始化作业内部，以显式`item_no`排序；不得把每个成员注册为`governance_release`或`outbox_event`。
16. 下载完成、操作员导出或交接、第三方HTTP成功分别只是模式动作证据；消费者应用回执、对账结论和检查点推进保持独立。
17. 只有对账确认固定来源的范围、版本、数量及摘要且不存在未解释缺口，模块才允许关闭初始化作业并建立或推进检查点；失败和差异只追加。
18. 自动化第三方入口仍使用服务身份和冻结公共API；受控导出不向第三方开放管理界面或数据库。容量实验环境由ADR-0110冻结为本机独占运行的WSL2 Anolis OS 8.9受限环境；声明式规则具体语法、编译或解释方式、私有执行组件物理位置，重复次数、峰值RSS/磁盘余量/时间阈值、结果聚合和最终数值上限，以及逐条接口幂等及暂存激活策略另行确认；容量画像逐字段分布由ADR-0109冻结。
19. 完整POC格式固定为根目录下仅有`manifest.json`和`records.csv`两个`STORE`条目的完整`application/zip`；不生成XLSX、裸CSV、压缩成员、其他容器、分片或同作业多格式变体。

47. 容量字段分布继续由同一验证fixture资产执行而不进入任何深模块：四个`N`画像逐可选输出字段精确70%有值/30%冻结空值，适用非空文本精确70%/25%/5%达到合法最大Unicode码点长度20%/50%/85%；普通画像使用无CSV结构字符的安全单字节基线，身份/代码/枚举/引用/摘要/严格模式字符串用合法确定性生成器并排除出长度分布。`W50`全部可选字段有值，字符串目标90%且唯一后缀计入预算，非字符串使用最长合法表示，字符串保持单字节。`E50`复用`N50`逐字段非空及码点长度分布，每个适用文本字段的非空单元格按稳定顺序形成纯中文、中文+ASCII、含逗号、含双引号、含逗号/双引号/LF五组各20%；适用/排除列按精确身份冻结，LF只进入多行字段，身份/代码/枚举/引用/摘要/金额/数值/日期/日期时间/布尔/不兼容模式字段排除。无合法字段、映射与Schema不一致、静默跳过或重分配均失败关闭；字符串长度用Unicode码点，容量用最终ZIP字节。Phase 01不得为此新建目录、依赖、接口、表、API、共享包或运行资产。

`E50`适用字段必须合法容纳全部五类字符；不允许LF的单行文本列整体排除在五组压力清单之外并保持普通内容，不能只跳过第五组或转移比例。

本节只冻结通用作业与制品证据的模块所有权、消费者交付配置治理主权及受控执行能力，不授权`release-distribution`编辑配置、理解厂商字段映射或改写领域语义。Phase 01只实现`SNAPSHOT_PULL`，不建立受控导出、技术重试、CSV/ZIP生成、`managed_export_artifact`字节持久化、取代关系、保留/清理任务、派生制品容量检查、画像生成器、容量试验装置或逐记录推送adapter；全部ABG门禁通过、冻结画像矩阵的前置容量实验完成且后续数值ADR冻结后，完整POC才在本深模块内部为`MANAGED_EXPORT_HANDOFF`建立合成仿真消费者所需的最小adapter、直接PostgreSQL持久化、制品生命周期和容量门禁，且只执行默认受控表示转换和确定性无压缩ZIP格式。集成后还须通过本模块实际路径及冻结公共API使用完全相同的画像版本和其余参数完成容量核验，才取得最终容量验收资格。`RECORD_PUSH`继续只保留结构接缝，不预建port。该新增薄切由G01至G12及U17至U20验证，G05/U19包含技术重试、G05/G06/U18包含确定性ZIP、G05/G06/G07/G12/U18包含存储原子性、G05/G07/G12/U18包含生命周期、G04/G05/G12/U19包含画像矩阵、两阶段容量证据、容量基线及超限失败的必需参数化子用例，完整POC总基线仍为72/20。

其中“冻结画像矩阵”和“两阶段完全相同的画像版本”均包含ADR-0109字段分布版本和精确适用字段清单；这些资产始终留在既有验证fixture边界，不会成为`release-distribution`配置主权或Phase 01预建实现。

## 12. 禁止结构

下列结构不得进入Phase 01：

- 全局`controllers`、`services`、`repositories`、`models`按技术种类横向组织全部能力。
- 一个路由、service、repository和model组成但几乎只转发的四层浅模块。
- `BaseService`、`BaseRepository`、`BaseController`、通用CRUD生成器或隐式继承钩子。
- 承载治理规则的`shared`、`common`、`utils`、`helpers`或跨模块domain包。
- 调用者拿到Kysely、`pg`连接、事务或repository后自行组合业务步骤。
- 跨模块直接查表、写表、导入内部文件、循环依赖或通过深层路径绕过`index.ts`。
- 为每个数据库表建立仅有一个adapter的repository port，并用内存实现替代真实PostgreSQL门禁。
- 使用通用命令总线、反射容器或动态插件机制隐藏真实依赖图。
- 独立`version`模块、`VersionService`、`BaseVersion`、`VersionedRepository`、通用版本CRUD或由配置驱动所有治理对象生命周期的通用状态机。
- 工作流、发布、审计或调用者直接更新`charge-catalog`、`price-list`或未来治理对象模块拥有的版本及生命周期表。
- `price-resolution`直接查询`price-list`表或草稿、导入其内部类型，或者把解析状态及金额回写为价表主数据。
- `price-list`、Fastify路由、组合编排或消费者复制院区回退、通用/专用选择、冲突处理和金额计算算法。
- `price-list`预先返回已择优的唯一价格条目，使`price-resolution`退化为保存结果的浅转发模块。
- 分别建立`publication`、`delivery`、`outbox`公开模块或通用仓储，再让它们通过事件ID传递内部步骤、互相查表或形成浅转发链。
- 领域模块、审计、路由或后台任务直接查写`release-distribution`拥有的发布、快照、Outbox、投递、尝试、检查点或回执表。
- `release-distribution`通过领域表、跨模块SQL、repository或提交后回调自行拼装发布内容，或者在缺少字段时按名称、当前版本或默认值推断领域语义。
- 领域模块直接写入快照存储、`release_snapshot`或Outbox，或者自行生成最终快照字节、投影载荷摘要或快照制品摘要。
- 通过数据库行、ORM/Kysely类型、REST DTO、任意无类型JSON、延迟加载器或事务句柄跨越内容投影seam。
- 在`release-distribution`、独立`projection-schema`模块、共享包或消费者代码中集中手写所有领域投影字段，使领域模块失去Schema主权。
- 修改或删除已经被快照引用的投影Schema版本，复用同一版本号表达不同字段或语义，或者按版本号外观自动判断兼容性。
- 为快照和变化契约平行维护手写OpenAPI、JSON Schema、DTO或消费者私有类型，或者让派生产物反向改写TypeBox定义源。
- 订阅声明`latest`、通配符、版本范围或SemVer兼容，运行时向消费者探测字段支持，或者覆盖旧订阅版本和预检结果。
- 认领或发送`BLOCKED_INCOMPATIBLE`投递、为其追加伪造发送尝试、推进任一水位，或者因某消费者不兼容而回滚领域发布或阻断其他消费者。
- 建立独立`compatibility`模块、通用投影转换器或降级服务，或者让`release-distribution`自动改写载荷、迁移Schema和选择未冻结的替代投影。
- 为同一发布登记第二个快照、并行Schema版本、消费者专用快照或降级副本，重打包或覆盖历史快照，或者用复制发布事实伪装消费者兼容。
- 合并发布与快照身份、把快照ID当作发布ID、保存可覆盖的“当前快照”，或者提前建立投影注册器、变体路由器、消费者快照选择器及未使用的多投影port。
- 把平台契约Owner实现为独立`contract-governance`模块、Schema编辑服务或`release-distribution`内部管理员，或者让该角色取得领域字段语义主权。
- 省略领域语义确认、平台契约确认、TypeBox/OpenAPI差异、兼容矩阵、仿真消费或影响分析，以消费者口头同意代替证据，或赋予消费者Owner发布批准、否决及延期权。
- 把纯契约升级的提交—终审例外应用于同时改变领域内容、成员、规则或生命周期的请求，合并同一主体的多个责任动作，或由服务身份执行人员审批。
- 使用含义模糊的单一`content_hash`同时代表领域内容、投影载荷和完整制品，或以双摘要相等/不等推断跨Schema领域语义等价。
- 把存储位置、投递、尝试、回执、审计链状态或其他可变运维元数据纳入摘要，或者把完整制品摘要嵌入其自身覆盖字节形成自引用。
- 按当前算法或序列化规则重算、覆盖、补写历史摘要，或者建立独立`digest`、`hashing`模块、服务及workspace取得制品或领域主权。
- 把权威快照写入本地/共享文件或S3兼容对象存储，建立数据库与外部存储双写、暂存提升、补偿状态机、未使用的存储port或第二个快照存储模块。
- 允许消费者、管理界面或测试直接读取`release_snapshot.artifact_bytes`，或在事件、API和客户端中泄露数据库表、列、连接及物理位置。
- 以TOAST或HTTP压缩后大小计量16 MiB护栏，自动拆分、截断、裁剪投影、改变序列化、生成替代快照或回退外部存储规避超限；或者把16 MiB写成全院初始化、生产或招标默认上限。
- 在Phase 01建立容量画像生成器、fixture目录、表、路由、模块、应用、workspace、共享包或依赖；在完整POC缺少七类冻结画像、使用错误行数或把表头计入行数；让`F00`参与上限推断；两阶段替换画像版本；以业务验收fixture代替容量fixture；混入重复、错误、缺失映射或不确定转换记录；允许外部变长字符串无有限最大长度；或者把画像行数解释为真实医院、生产规模、容量上限、SLA或招标参数。
- 在Phase 01建立字段分布fixture、目录、配置、表、路由、模块、应用、workspace、共享包或依赖；在完整POC以随机近似或字段名称推断代替逐字段精确分布，违反普通画像70%/30%、70%/25%/5%和20%/50%/85%，违反`W50`的100%/90%或唯一后缀预算，违反`E50`复用`N50`及五类各20%，允许非法LF、无合法字段时静默跳过或重分配，或者混同Unicode码点长度与最终ZIP字节。
- 把轮询、租约认领、发送、重试或投递投影更新暴露为供任意调用者拼装的外部接口，或通过内部HTTP回环调用同进程模块。
- 因模块统一而在发布事务中执行网络调用、让后台状态机自行改变领域版本，或让平台侧检查点代替仿真消费者内部水位。
