# 科室主数据POC调整方向

状态：总体方向、核心层级语义及POC操作范围已确认
更新日期：2026-07-30

本次调整不改变以下POC边界：

- 仍然只服务一个医院治理主体，可包含多个院区。
- 仍然不接真实消费系统，只使用仿真消费者。
- 仍然覆盖人员主数据、科室主数据、医疗机构诊疗科目代码值域、价表字典和数据元五类治理对象。
- 仍然验证导入与增删改查、全流程审计、治理闭环、版本变更和发布回退。
- 不扩展为生产可用性、灾备、真实临床迁移、集团联邦注册或招标基线项目。

## 2. 总体判断

“三层、四域、两条时间线”应成为科室主数据POC的主设计框架，但需要作以下精确定义：

1. **三层**回答同一科室如何拥有稳定身份、历史版本和多视角投影。
2. **四个语义域**回答科室与组织、服务能力、物理地点、术语及代码映射之间的对象边界；它们不是医院十五个数据域中的四个新建设范围。
3. **两条业务时间线**回答主数据何时正式生效、各消费者何时迁移；平台记录时间继续作为独立审计时间轴保留。
4. 多视角层级与四个语义域相互正交：行政、运营、病案等是投影视角，组织、服务、地点、术语映射是对象类别。

## 3. 三层模型

### 3.1 稳定实体层

`Department`只表达科室业务身份：

- `department_id`永久且不可复用。
- 不以名称、院内代码、源系统代码或统计代码充当身份。
- 改名、普通属性调整、层级调整、停用与恢复不改变身份。
- 拆分和实质性合并产生新的科室身份。

稳定实体层不保存可覆盖的当前名称、当前父节点或当前状态。需要快速查询的当前态只能是派生投影，不是事实源。

### 3.2 不可变版本层

`DepartmentVersion`表达同一科室在某一业务时段的正式语义：

- 正式名称、简称、科室类型、诊疗科目映射适用性和生命周期状态。
- 业务有效区间与平台记录区间。
- 结构版本、变更事件、发布版本和审计来源。
- 版本内容不可覆盖；更正形成新版本。

诊疗科目映射适用性由权威组织来源提供初值、医务管理Owner审核发布，取值为必需映射的门诊诊疗、必需映射的临床实际业务、不必需映射的医技、不必需映射的辅助或待判定；不得按科室名称或层级位置推断。

同一科室稳定身份同时承担实际诊疗职责和医技或辅助职能时，实际诊疗职责优先并归入必需映射；诊疗门诊与医技科室若为不同稳定身份则分别判定，纯医技和纯辅助科室仍可豁免。

标识符、别名和源系统交叉码分别版本化，不塞入科室主表JSON：

- `DepartmentIdentifier`：院级正式码、旧码、临时代码及有效期。
- `DepartmentAlias`：正式简称、历史名称、视角展示别名及有效期。
- `DepartmentXref`：源系统、源对象、源代码到稳定科室ID的映射及有效期。

### 3.3 口径投影层

行政、运营、病案、财务、统计等口径均作为独立的`HierarchyView`治理对象：

- 每个视图拥有独立用途、Owner、数据管家、权限、规则、审批与发布版本。
- 父子关系只属于指定视图，科室主实体不保存通用`parent_department_id`。
- 真实科室节点引用全院统一的科室稳定ID。
- 允许“大内科板块”“运营中心组”“病案分类组”等受限的视图内分组节点；它们只在一个视图内拥有稳定身份、版本和业务有效期，并随该视图发布。
- 分组节点不取得科室稳定ID，不得跨视图复用，也不得成为人员、业务事实、源系统交叉码、服务或地点的科室引用目标。
- 分组以后成为真实科室时必须新建科室稳定ID并显式关联，不能原位转换；决策记录见[ADR-0030](../adr/0030-view-local-grouping-nodes-in-department-hierarchies.md)。
- 每次发布形成不可变完整结构快照，记录节点、边、引用的科室或分组版本、发布时展示名称、有效时间、摘要和来源发布。
- 历史快照不得动态解析当前名称；查询时可附加明确标注的当前名称，但该信息不属于快照，不得覆盖快照名称或改变快照摘要。决策记录见[ADR-0031](../adr/0031-freeze-names-and-referenced-versions-in-hierarchy-snapshots.md)。
- 不同视图中的父节点、子树或显示名差异是合法的视角差异。

单个视图内部采用严格树或森林：任一业务有效时点每个节点最多有一个父节点，同一科室只能出现一次，循环、多父和重复放置均阻断发布。矩阵式多父归属通过另一个独立层级视图或非层级多对多关系表达，后者不自动参与子树汇总、权限继承或数据分摊；决策记录见[ADR-0029](../adr/0029-strict-tree-per-department-hierarchy-view.md)。

## 4. 四个语义域

为避免与医院“数据域目录”混淆，本设计将报告中的“四域”正式称为“科室模型四个语义域”。

| 语义域 | 核心对象 | 与科室的关系 | POC深度 |
|---|---|---|---|
| 组织语义域 | 科室身份、版本、演变血缘、层级视图 | 科室是谁、如何演变、在各视角如何组织 | 完整验证 |
| 服务语义域 | 服务能力、专科能力、可提供服务 | 科室在某时段提供什么服务 | 最小样例关系，不建设完整服务目录 |
| 地点语义域 | 院区、诊区、病区或其他物理地点 | 科室或服务在何处运行 | 院区加最小合成地点样例，不扩展床位治理 |
| 术语映射语义域 | 标识、医疗机构诊疗科目代码值域、标准代码、ConceptMap式映射、源系统交叉码 | 不同系统和上报口径如何解释同一对象 | 与科室主数据、数据元联动验证 |

四个语义域之间只通过稳定标识和版本化关系连接：

- 科室不等于地点；搬迁通常不改变科室身份。
- 科室不等于服务；服务能力新增或暂停通常不改变科室身份。
- 科室不等于成本中心或统计分类；这些属于指定视图或映射。
- 科室与诊疗科目采用零到多对零到多的独立映射，明确等同、科室范围较窄、科室范围较宽或仅相关，不把标准分类变成科室属性。
- 科室诊疗科目映射冻结审批时校验的目标代码版本；无关代码新增不影响既有映射，目标语义变化、停用或替代只触发显式重审，不自动迁移。
- 病区、护理单元、门诊单元不能因为当前名称相似就自动判定为科室。

### 4.1 诊疗科目来源与采纳版本

官方诊疗科目名录及其每份正式增补、修订文件分别作为不可变来源证据原样留存。平台把多个官方来源整理为完整代码快照时，发布对象正式称为“诊疗科目院内采纳版”，不得冒称国家官方整版或国家最新版。

每个院内采纳版必须记录：

- 完整来源文件清单、发布机构、文号、发布日期、生效日期、来源地址和文件摘要。
- 来源合并顺序、转换规则版本、人工处置记录和相对上一采纳版的差异。
- 业务生效时间、平台记录时间、审批发布信息和完整内容摘要。
- 基线版以及至少一个纳入正式增补或修订的新版。

新官方来源导入后只形成新的采纳版草稿，经校验、复核和审批后才能发布；不得覆盖既有来源证据或已发布采纳版。决策记录见[ADR-0039](../adr/0039-separate-official-source-evidence-from-hospital-adopted-releases.md)。

POC的基线版和修订版均为完整诊疗科目代码快照。科室映射使用不少于十二个跨院区合成科室，覆盖全部关键映射、适用性和版本变化场景，但不追求全院科室或全部诊疗科目的映射覆盖率；决策记录见[ADR-0040](../adr/0040-full-code-snapshots-with-bounded-synthetic-mappings.md)。

### 4.2 POC代表性数据元

POC不建设完整国家数据元目录，而使用四个稳定标识、独立版本化的数据元验证不同约束：

| 数据元 | 约束类型 | POC联动对象 |
|---|---|---|
| 科室稳定标识 | 主数据引用 | 科室主数据及其生命周期 |
| 诊疗科目代码 | 编码绑定 | 指定诊疗科目院内采纳版 |
| 价表价格金额 | 金额、币种、精度和范围 | 价表字典 |
| 业务生效时间 | 日期时间、格式、时区和时间轴 | 所有版本化治理对象 |

每个数据元记录稳定ID、不可变版本、定义、表示类型、约束、来源、Owner、审批和发布历史。该范围覆盖主数据引用、编码、金额和时间四种典型约束，但不承诺登记全部业务字段；决策记录见[ADR-0041](../adr/0041-four-representative-data-elements-in-poc.md)。

CSV、XLSX、JSON、REST和管理界面的具体字段通过版本化的数据元使用关系复用统一定义。使用关系冻结目标数据元版本，并记录位置、字段路径、必填性、出现次数、展示标签和局部约束；局部只能收紧约束，不能放宽或改义，数据元新版不会自动升级已发布使用关系。决策记录见[ADR-0042](../adr/0042-reuse-data-elements-through-versioned-usages.md)。

四个代表性数据元均采用错误级强制校验：科室稳定标识必须满足业务时点引用规则，诊疗科目代码必须属于冻结的院内采纳版，价格金额必须满足币种、精度和范围，业务生效时间必须满足格式、时区和区间规则。单条记录失败不回滚同批次成功记录；历史结果按冻结的数据元、绑定目标和规则版本解释。决策记录见[ADR-0043](../adr/0043-error-level-validation-for-four-poc-data-elements.md)。

## 5. 时间模型：两条业务时间线加一条记录时间轴

两份报告对“双时间”的含义不同：

- 报告（3）强调正式生效时间与运营迁移时间。
- 报告（2）强调业务有效时间与系统记录时间。
- 现有ADR-0019已经确认业务有效时间与平台记录时间的双时态。

已确认不相互替代，而采用以下结构；决策记录见[ADR-0028](../adr/0028-department-business-and-record-time-semantics.md)：

### 5.1 主数据生效时间线

表示科室版本、关系或视图结构在医院治理意义上何时正式有效：

- 使用闭开区间`[valid_from, valid_to)`。
- 支持计划未来生效、历史回溯和迟到更正。
- 法定批文日期在适用时作为变更依据记录；不强迫所有科室变更都具有“法律时间”。

### 5.2 运营迁移时间线

表示消费者从旧版本、旧代码或旧视图迁移到新发布的过程：

- 预装载、兼容期或双跑、切换、停止旧码、回执确认分别留痕。
- 运营窗口属于变更发布与消费者迁移计划，不属于科室实体版本。
- 不设置一个全局`operational_start/end`覆盖所有系统；每个消费者或消费组分别记录迁移节点。
- POC由两个以上仿真消费者模拟不同切换时间、幂等重试和失败补偿。

### 5.3 平台记录时间轴

表示平台何时获知、创建、审批、发布、更正或补偿某一状态：

- 保留ADR-0019的双时态查询能力。
- 回答“当时业务上有效什么”和“平台当时已经知道什么”两个不同问题。
- 它是审计和迟到更正所必需的记录时间轴，不与运营迁移时间合并。

因此，本方案中的“两条时间线”特指两条业务时间线；平台记录时间仍然存在，形成“两个业务时序加一个审计时序”。

## 6. 建议数据结构

| 结构 | 主要职责 | 核心关系 |
|---|---|---|
| `department` | 稳定科室身份 | 一对多版本、标识、血缘成员 |
| `department_version` | 不可变业务版本 | 双时态、业务属性、映射适用性、来源与审核、实体版本号 |
| `department_identifier` | 院级码、旧码、临时代码 | 稳定科室ID、标识体系、有效期 |
| `department_alias` | 简称、历史名称、视角别名 | 稳定科室ID或视图节点、有效期 |
| `department_xref` | 源系统交叉码 | 源系统业务键到稳定科室ID |
| `department_change_case` | 一次协调性变更主题 | 关联多个独立治理对象的变更请求 |
| `department_change_member` | 拆分/合并的来源与目标成员 | 角色、说明，可选但不自动执行的分析权重 |
| `department_lineage_edge` | 前身与后继血缘 | 拆分、合并、身份替代 |
| `hierarchy_view` | 视角定义与治理责任 | 行政、运营、病案等 |
| `hierarchy_view_release` | 视图发布版本及完整快照清单 | 节点与边版本、引用版本、快照展示名称、内容摘要 |
| `hierarchy_group` | 视图内非科室分组身份 | 只能属于一个视图，不引用科室稳定ID |
| `hierarchy_node_version` | 视图内科室节点或分组节点 | 只能引用稳定科室ID或视图内分组身份之一 |
| `hierarchy_edge_version` | 指定视图内的父子关系 | 双时态、有效区间、结构校验 |
| `department_affiliation_relation` | 非层级的中心、协作组或归责单元归属 | 多对多、角色、双时态、可选且经批准的解释性权重 |
| `department_service_relation` | 科室与服务能力关联 | 多对多、双时态 |
| `department_location_relation` | 科室与院区/地点关联 | 多对多、双时态 |
| `standard_source_artifact` | 官方名录、增补或修订的不可变来源证据 | 发布信息、来源地址、文件摘要、获取时间 |
| `diagnostic_subject_adopted_release` | 院内采纳的完整诊疗科目代码快照 | 来源清单、转换规则、版本差异、双时态、审批和内容摘要 |
| `adoption_source_member` | 院内采纳版与来源证据的组成关系 | 合并顺序、适用范围、人工处置说明 |
| `data_element` | 数据元稳定身份 | 一对多不可变版本 |
| `data_element_version` | 数据元业务定义与约束 | 表示类型、约束、来源、Owner、双时态和审批 |
| `data_element_binding` | 数据元与主数据或值域的绑定 | 目标稳定身份、校验版本、错误级最低强度和绑定规则 |
| `data_element_usage` | 模板、接口或界面字段对数据元版本的使用 | 使用位置、字段路径、必填性、出现次数、展示标签和收紧约束 |
| `department_diagnostic_subject_mapping` | 科室与诊疗科目代码的独立治理映射 | 双方多对多、映射语义、目标代码校验版本、双时态、依据、审批和版本 |
| `diagnostic_subject_mapping_issue` | 映射缺失或目标变化的待处置事项 | 科室与映射版本、触发原因、影响消费者、阻断级别、状态和处置审计 |
| `transition_plan` | 某次发布的运营迁移计划 | 主数据生效点、影响消费者 |
| `transition_target` | 单个消费者的迁移状态 | 预装载、切换、回执、重试、补偿 |
| `audit_event` | 不可变操作与审批审计 | 操作者、理由、前后版本引用、结果 |

当前态查询、物化视图或缓存可以存在，但必须可由上述版本事实重建。

## 7. 变更与发布流程调整

建议的科室变更闭环如下：

1. 通过CSV、XLSX、JSON API或管理界面形成草稿。
2. 按来源业务键执行批次内判重、原批次幂等重试和新批次版本判断。
3. 校验权威来源提供的诊疗科目映射适用性初值；混合职能科室以正式的实际诊疗职责优先，缺失或无法确认时进入待判定，不根据名称或层级补值。
4. 判定变更类型：改名、状态变化、映射适用性变化、视图调整、地点变化、服务变化、拆分、合并或身份替代。
5. 创建协调性`change case`，声明主数据生效时间、依据和影响范围。
6. 对科室版本、标识、交叉码、层级视图、服务、地点、术语映射及其他治理对象执行影响分析。
7. 门诊诊疗科室或临床实际业务科室缺少有效诊疗科目映射时，形成映射完整性事项；医技和辅助科室不适用该强制规则。
8. 新官方诊疗科目文件先登记为不可变来源证据，再编制新的院内采纳版草稿；来源清单、合并顺序和转换规则均须审计。
9. 诊疗科目院内采纳版发布后比较受影响代码；语义变化、停用或替代产生映射重审事项，无关新增不触碰既有映射。
10. 各治理对象和各层级视图分别形成变更请求，分别校验、审批和发布；只建立关联，不做跨对象原子发布。
11. 每个发布生成不可变发布清单和内容摘要；层级视图额外生成完整结构快照。
12. 为仿真消费者建立迁移计划，模拟预装载、不同时间切换、回执、失败重试和补偿。
13. 生效后执行引用阻断、影响事项核验、消费者回执核验和审计校验。
14. 全部必需事项完成或经授权放弃后关闭；发现错误时生成补偿发布，不覆盖历史或重新激活旧版本。

主数据对象内部的一次发布可以使用本地强事务，但不能借此把科室、多个层级视图和其他治理对象绑成一个跨对象事务。

## 8. POC验证计划

### 增量一：模型与契约基线

- 冻结三层模型、四个语义域和时间词汇。
- 明确科室身份、版本、标识、交叉码、血缘、视图和快照结构。
- 为科室主数据建立CSV、XLSX和JSON结构版本。
- 为CSV、XLSX、JSON、REST和管理界面的代表性字段建立数据元使用关系并冻结目标数据元版本。
- 落实单视图严格树/森林、非层级归属关系、受限的视图内分组节点，以及发布时名称与引用版本冻结规则。

### 增量二：导入与基础生命周期

- 验证新增、查询、修改生成新版本、草稿删除和已发布失效。
- 验证批次内重复、同键冲突、原批次重试与新批次同键变更。
- 验证四个数据元的错误级约束逐字段返回，失败记录与同批次成功记录相互隔离，重试时忽略已成功记录。
- 验证改名、停用、恢复和弃用。
- 验证映射适用性初值、医务管理Owner审核、待判定和分类变更均形成可追溯版本。
- 验证当前、业务时点、平台记录时点、版本历史和差异查询。

### 增量三：拆分合并与血缘

- 验证一拆二和二并一均创建新稳定身份。
- 验证前身被替代、后继关系、影响事项和历史事实不改写。
- 验证分析权重不能自动迁移历史引用或人员归属。
- 验证错误发布通过补偿版本处理。

### 增量四：多视角层级与快照

- 完整建立行政、运营、病案三个独立层级视图。
- 对同一科室设置不同父节点和不同子树。
- 验证独立Owner、治理对象级权限、提交审批分离和独立发布。
- 验证循环、多父和同一科室重复放置均被阻断，并验证多对多归属关系不影响子树汇总。
- 验证分组节点随所属视图版本化和发布，且跨视图复用、科室型业务引用及原位转为科室均被阻断。
- 验证科室改名后旧快照的结构、引用版本和快照名称保持不变，当前名称只能作为明确标注的附加信息展示。
- 验证发布快照、子树查询、历史回溯和版本差异。
- 财务与统计只保留为可注册的视图类型和通用接口契约，不导入真实口径、不建立完整样例、不纳入必验范围。
- 验证能够通过同一套治理机制注册新的视图类型，不将行政、运营、病案三种视图硬编码；决策记录见[ADR-0032](../adr/0032-limit-operational-hierarchy-views-in-poc.md)。

### 增量五：四个语义域的最小闭环

- 组织语义域完整验证。
- 服务语义域建立至少一个服务能力及其科室关联样例。
- 地点语义域建立多院区和至少一个合成地点迁移样例。
- 术语映射语义域导入医疗机构诊疗科目代码值域及正式增补修订，并联动科室主数据、数据元、院级码和源系统交叉码；决策记录见[ADR-0033](../adr/0033-use-diagnostic-subject-codes-as-representative-value-set.md)。
- 验证官方源文件原样留证，基线与增补修订分别形成两个完整院内采纳版，且来源清单、转换规则、差异和审批链可复现。
- 验证院内采纳版不会被标记为国家官方整版或国家最新版，新来源导入不会自动覆盖已发布版本；决策记录见[ADR-0039](../adr/0039-separate-official-source-evidence-from-hospital-adopted-releases.md)。
- 使用不少于十二个跨院区合成科室覆盖全部关键映射场景，不以全院映射率或全部诊疗科目已映射作为验收指标；决策记录见[ADR-0040](../adr/0040-full-code-snapshots-with-bounded-synthetic-mappings.md)。
- 建立科室稳定标识、诊疗科目代码、价表价格金额和业务生效时间四个数据元，验证稳定ID、版本、约束、审批发布和跨对象联动；决策记录见[ADR-0041](../adr/0041-four-representative-data-elements-in-poc.md)。
- 验证同一数据元可被CSV、XLSX、JSON、REST和管理界面复用，局部约束只能收紧，数据元新版只产生影响事项而不自动升级使用关系；决策记录见[ADR-0042](../adr/0042-reuse-data-elements-through-versioned-usages.md)。
- 验证四个数据元均执行错误级强制校验，违规只使当前记录失败，历史按冻结版本复现；决策记录见[ADR-0043](../adr/0043-error-level-validation-for-four-poc-data-elements.md)。
- 诊疗科目代码不得充当科室稳定ID，也不得自动生成科室层级。
- 验证一个综合科室关联多个诊疗科目、多个实际科室关联同一诊疗科目，以及行政后勤科室无映射的场景。
- 验证等同、科室范围较窄、科室范围较宽和仅相关四类映射语义，并验证映射变更形成新版本。
- 验证名称相似、上下级变化和拆分合并均不会自动创建或继承映射；决策记录见[ADR-0034](../adr/0034-versioned-many-to-many-department-subject-mappings.md)。
- 验证门诊诊疗科室和临床实际业务科室缺少有效映射时形成完整性事项，但科室主数据仍可独立发布。
- 验证医技和辅助科室不要求映射，映射缺失仅阻断依赖映射的仿真消费者就绪或相关口径发布；决策记录见[ADR-0035](../adr/0035-layered-blocking-for-required-subject-mappings.md)。
- 验证名称和层级相似不会改变映射适用性，待判定状态保持显式且阻断相关消费就绪；决策记录见[ADR-0036](../adr/0036-explicit-governed-mapping-applicability.md)。
- 验证同一稳定身份的医技科室正式承担诊疗职责时按必需映射处理，而独立稳定身份的诊疗门诊与纯医技科室分别判定；决策记录见[ADR-0037](../adr/0037-clinical-duty-takes-precedence-for-mixed-departments.md)。
- 验证无关代码新增不改变既有映射，名称或说明变化触发提示性复核，语义变化、停用或替代触发阻断性重审。
- 验证历史映射继续绑定原目标版本，任何延续确认或替代代码迁移均形成新映射版本且不改写历史；决策记录见[ADR-0038](../adr/0038-pin-mapping-target-versions-and-require-explicit-review.md)。
- 不建设完整床位、护理单元、服务目录或真实业务事实域。

### 增量六：运营迁移仿真与闭环验收

- 安排一个未来生效的科室拆分或视图调整。
- 至少两个仿真消费者采用不同预装载和切换时间。
- 验证旧码兼容窗口、幂等重试、失败补偿、消费回执和关闭条件。
- 验证主数据已生效但消费者尚未切换的过渡状态可被查询和审计。
- 验证发布清单、视图快照、消费者应用结果和审计链摘要一致。

## 9. 关键验收场景

| 场景 | 必须证明的能力 |
|---|---|
| 科室改名 | ID不变，新版本生效，历史快照名称不漂移，当前名称只能附加展示 |
| 暂停与恢复 | ID不变，停用期阻断新引用，恢复形成新版本 |
| 永久弃用 | 无后继，不得恢复原ID |
| 一拆二 | 新ID、血缘、多个视图独立处置、历史不改写 |
| 二并一 | 新ID、多前身血缘、旧科室被替代 |
| 行政与运营父级不同 | 视角差异合法且可独立发布 |
| 视图内分组节点 | 能组织真实科室，但不能充当科室引用目标或跨视图身份 |
| 病案视图历史快照 | 指定发布版本可完整复现 |
| 地点迁移 | 地点关系改变但科室身份按规则延续 |
| 服务能力调整 | 服务关系变化不误判为科室身份变化 |
| 诊疗科目值域变更 | 标准来源、版本、增补修订、差异及历史代码均可追溯 |
| 官方增补文件导入 | 原文件证据不变，形成待审核院内采纳版草稿，不自动发布 |
| 院内采纳版回溯 | 能还原全部来源、合并顺序、转换规则、审批和完整代码快照 |
| 合成映射覆盖 | 不少于十二个跨院区科室覆盖一对多、多对一、四类语义、必需豁免、混合职能、演变和代码变化 |
| 四类数据元约束 | 主数据引用、编码绑定、金额和时间约束均可独立版本化、审批、发布和审计 |
| 数据元跨载体复用 | CSV、XLSX、JSON、REST和界面引用同一数据元定义，局部只能收紧且升级需显式发布 |
| 数据元错误级校验 | 四个数据元违规均阻断当前记录，逐字段留错且不回滚同批次成功记录 |
| 科室诊疗科目映射 | 多对多和四类映射语义可表达，变更版本化且不自动继承 |
| 强制映射缺失 | 科室可独立发布，完整性事项保持开放，相关消费者和口径被阻断 |
| 医技或辅助科室无映射 | 不产生强制映射错误，也不被错误归类为诊疗科室 |
| 映射适用性待判定 | 科室可发布但相关消费不能就绪，名称和层级不得被用于自动补值 |
| 混合职能科室 | 同一身份承担实际诊疗职责时必需映射，独立身份则分别判定 |
| 诊疗科目新增无关代码 | 既有映射及历史消费结果保持不变 |
| 映射目标语义变化或停用 | 历史映射不改写，产生显式重审并阻断未来相关消费 |
| 标准码变更 | 旧码和历史映射可解释，源代码不成为企业身份 |
| 迟到更正 | 业务时间与平台记录时间返回不同但可解释结果 |
| 分阶段切换 | 主数据生效、消费者预装载与消费者切换状态分别可查 |
| 回退 | 生成补偿发布，错误版本和审计历史仍保留 |

## 10. 不直接采纳的报告建议

以下内容不进入当前方向：

- 不保留一个跨视角通用`parent_dept_uid`。
- 不把department、ward、clinic unit、service line和cost center全部塞入一个通用组织单元类型。
- 不用`ACTIVE/INACTIVE/CLOSED`覆盖已确认的在用、停用、弃用和被替代语义。
- 不把草稿状态与科室业务状态放在同一生命周期字段中。
- 不把运营迁移窗口直接放入科室版本并假定所有消费者同时切换。
- 不把拆分比例或合并权重解释为自动迁移人员、事实或历史报表的指令。
- 不因统计或病案映射未完成而阻止所有其他治理对象永久发布；应阻断相关视图发布并形成影响事项。
- 不建设完整财务或统计层级口径，也不将其列为POC必验范围。
- 不通过重新激活旧实体版本完成回滚；使用新的补偿发布。
- 不采用九至十二个月生产实施路线、真实系统灰度切换或集团联邦注册作为POC承诺。

## 11. 已确认决策

已确认“两条时间线”是主数据生效时间线和运营迁移时间线，同时保留平台记录时间轴。

已确认单个层级视图采用严格树或森林，多父归属通过另一个视图或非层级关系表达。

已确认允许受限的视图内分组节点，但它不取得科室稳定ID，不能充当真实科室，也不能跨视图复用。

已确认层级视图快照冻结发布时展示名称及引用版本，当前名称只能作为明确标注的快照外附加信息。

已确认POC只操作性覆盖行政、运营、病案三个层级视图；财务和统计只保留可配置扩展能力，不纳入完整样例或必验范围。

已确认医疗机构诊疗科目代码值域为POC代表性标准值域，它只通过治理映射关联科室，不充当科室身份或层级。

已确认科室与诊疗科目采用零到多对零到多、有类型、独立版本化的治理映射，不根据名称、层级或演变关系自动继承。

已确认门诊诊疗科室和临床实际业务科室必须具有有效诊疗科目映射，医技和辅助科室不强制映射；缺失映射不阻断科室主数据发布，只阻断相关消费就绪或口径发布。

已确认诊疗科目映射适用性由权威组织来源提供初值、医务管理Owner审核，以科室版本显式治理，禁止根据名称或层级推断。

已确认纯医技和纯辅助科室可豁免映射，但同一稳定身份同时承担实际诊疗职责时，以诊疗职责优先并强制映射；不同稳定身份分别判定。

已确认科室诊疗科目映射冻结审批时的目标代码版本；无关新增不影响，语义变化、停用或替代触发显式重审且不得自动迁移。

已确认官方诊疗科目源文件原样留证，平台汇编结果作为院内采纳版发布并保留完整来源清单，不得冒称国家官方整版或国家最新版。

已确认POC发布两个完整诊疗科目代码快照，并以不少于十二个跨院区合成科室覆盖关键映射场景，不追求全院映射。

已确认POC使用科室稳定标识、诊疗科目代码、价表价格金额和业务生效时间四个代表性数据元，不建设完整数据元目录。

已确认具体字段通过版本化使用关系复用统一数据元定义，局部只能收紧不能改义，数据元升级不得自动传播。

已确认四个代表性数据元均采用错误级强制校验，违规只使当前记录失败，同批次成功记录不回滚，历史按冻结版本解释。
