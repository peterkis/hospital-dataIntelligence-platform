## Stable identity and boundaries

The platform uses its existing PostgreSQL `uuidv7()` strategy for personId and
personVersionId. Callers cannot supply personId in a create-subject command.
Identity never changes, recycles or becomes an employee/department/account code.
Names and dates are not uniqueness keys: identical facts can represent distinct
subjects until separately authorized identity-resolution work establishes otherwise.

| Separate authority | A-01 boundary |
|---|---|
| Engagement | No employment type, status, active flag or re-employment model |
| Assignment | No current department, campus, placement, rotation or secondment |
| Assignment Role | No job, position, professional title or role facts |
| Credential | No license, certificate or qualification facts |
| Identifier / Source Mapping | No national identifier, employee code, source key, phone or email |
| IAM | No account, OIDC, Keycloak or security-principal identity binding |
| Patient / EMPI | No patient identifiers, matching or cross-domain merge |

The create command requires an explicit `CONFIRMED_HOSPITAL_PERSONNEL` eligibility
declaration by the authorized caller. This is an admission precondition, not a
stored personnel type or an Engagement implementation. Patient, family, visitor,
supplier, service-account, machine and bot declarations fail closed. The platform
cannot infer real-world eligibility or person equality from names and birth dates.
That evidence remains the Person Owner's responsibility; this prototype uses only
synthetic declarations. Authentication never creates a Person.

The database's created_by reference is creation/audit provenance, not a binding
between the subject and the actor. The subject ID differs from the creating
security principal. Active human actors and the one hospital Person governance
object are required. Service actors fail closed even before object permission
evaluation; no approval, review or service-principal rule is weakened.

Native migration: `0020_person_master_subject_core.sql`; registry count **19 → 20**.
Earlier migrations remain byte-identical. `person_master` belongs exclusively to
the `person-master` deep module in table-ownership.json. Database-derived Kysely

| Table | Columns and responsibility |
|---|---|
| person_master.person_subject | person_id, governance_object_id, creation_request_id, created_at, created_by; stable technical identity and creation provenance only |
| person_master.person_subject_version | person_version_id, person_id, governance_object_id, version_no, canonical_name, birth_date, business_valid_from/to, recorded_from, created_by, request_id, operation_hash, generated business_period |

PKs protect both UUID identities. Composite FK (person_id, governance_object_id)
prevents cross-scope versions. Unique keys protect (person_id, version_no),
(person_id, request_id), and (governance_object_id, creation_request_id). PK/unique
indexes support subject lookup, ordered history and request retry; there is no
name, fuzzy-search, roster or speculative index. A partial unique registry index
allows one Person Master authority for this single-hospital context.

The insert trigger locks the stable subject, requires the next version number,
strictly increasing finite record time, a valid Person scope and human actor.
Deferrable first-version constraint rejects committing an orphan stable subject.
Both tables reject UPDATE, DELETE and TRUNCATE. Public mutation privileges are
revoked. The application exposes no delete operation. Controlled DBA/DDL access
is outside the normal application contract, as in ADR-0020.

## Application, transactions and audit

The public internal capability provides createPersonSubject,
createPersonSubjectVersion, getPersonSubject, getPersonSubjectVersion,
listPersonSubjectVersions and findPersonSubjectAsOf. The composition root binds
the existing RequestContext and TransactionRunner to Person, authorization and
audit instances in one transaction. Database/factory wiring stays in composition;
the Person module never reads Department, Workflow, Release or account tables.

Person scope uses the existing object_permission_grant authority with only two
new codes, PERSON_MASTER_CORE_READ and PERSON_MASTER_CORE_WRITE. Hospital-level
grants are required. No Person ACL, owner table or permission system is introduced.
The mutation authority is the explicitly granted Person Core owner capability;
these commands do not publish or bypass a not-yet-built workflow.

Subject, first version and PERSON_SUBJECT_CREATED / PERSON_SUBJECT_VERSION_CREATED
audit events commit atomically. A failure after either audit insertion rolls back
all business and audit facts. Later version and audit commit atomically as well.
Sensitive reads append PERSON_SUBJECT_READ with IDs, query kind and temporal
criteria. Audit payloads omit names/birth dates, retain request/actor/correlation
provenance, pass the existing payload safety guard and use the existing hash chain.
Existing authorization-decision evidence retains its independent persistence
convention; denied operations create no Person facts.

Scope, service-actor and inactive-actor denials append PERSON_CORE_ACCESS_DENIED
through the same audit module in an independent transaction before rejecting the
business request. The record keeps actor/request context, requested governance
object, operation and stable reason code. It survives business rollback. Ordinary
missing-grant denial retains the existing authorization_decision evidence.

RequestContext.requestId identifies a concrete operation. Create retries are
serialized on object + request ID; persisted first-version operation hash and
creator must match. A mismatching retry fails with PERSON_OPERATION_CONFLICT.
Next-version retries are scoped to person + request ID under the subject row
lock. Neither retry makes a second subject/version/audit mutation. Operation
identity never comes from matching person facts. No idempotency table is added.

## Immutable versions and bitemporal semantics

All stored version columns remain immutable, including recorded_from. The
business interval is [business_valid_from, business_valid_to); null end means
unbounded. Record time is assigned by platform.local_now() after acquiring the
subject lock, independent of caller-supplied occurrence time. Version numbers,
not timestamps, own the per-person order. DATE and timestamp/tsrange without
time zone retain the existing driver string representation; Z/offset inputs
fail at the module boundary rather than being stripped by PostgreSQL.

At business time B and record time R, the read selects the highest version_no
whose business period includes B and whose recorded_from is <= R. A correction
supersedes earlier assertions only over its declared business period. Thus, at
each B, the implicit record period ends when the next applicable assertion is
recorded. Uncovered business periods retain their previous facts; a bounded
correction does not erase earlier/future unaffected intervals. This implements
ADR-0019's two questions without a mutable recording-closure column or a generic
version service. No additional clock, event-sourcing subsystem or public temporal
query API is created. Latest-version inspection is explicitly different from an
as-of query and is not an employment-status computation.

The unreleased 0020 table comment was refined to describe this applicable-period
rule. That exact COMMENT statement was executed from the native migration source;
table/constraint structure and migration registry were unchanged, then codegen and
authority verification were repeated. No 0001–0019 migration was edited.
