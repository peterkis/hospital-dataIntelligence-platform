# P1-05 组织工作簿导入

实施基线：`e4ee252ac331bcbfdf83b8542df062d84efcb96a`，P1-04 PR #16 已合并。持久库实施前核实为 migration 0064、OID 206108；完成与部署状态以本票交接证据为准。

## 输入与领域责任

一个 XLSX 必须有 ORG01/ORG02/ORG03 三个具名、可见工作表，每表准确表头；允许单表为空，整包不能空。STRICT_ORG_BUNDLE_V1 沿用现有 ZIP/XML 安全解析器与有界 worker。清单逐物理行声明意图、typed 引用、证据和采纳版本，不能改写源单元格。

原文件和清单分别存入公共受保护材料；bundle_revision 只保留准确绑定与摘要。源字段与微秒时间原值保留在受保护载荷，规范化结果交给已有 Owner。JOB_ALIAS 在 job/revision/dataset 内解析，PLATFORM_REF 必须显式声明；名称和 UUID 外观都不提供身份推断。

作业的 ORG01 契约保持传输锚点身份；更新三表任一契约绑定通过新 revision 完成。公共解析/校验账本的 contractVersionId 和 ruleVersion 表示该传输锚点，各表实际解释版本在组合绑定、签名解析载荷及校验 dependencies 中明确记录。新绑定必须仍属于准确文件 CORE，并在核验、批准和应用前检查当前有效版本；旧 revision 的核验与预授权不跨版本复用。文件 CORE 作业不能改用旧单表策略来绕过整包原子性。

## 事务路径

1. 文件接收与 typed 清单在同根事务建立 revision；延迟约束拒绝缺少任何一项绑定的提交。
2. 按各表准确契约进行字段检查，编译最多 100 条有依赖的领域命令；工作表和行顺序不代表执行顺序。
3. 管理员显式预授权逻辑配对；核验人读取准确原始单元格、清单与证据，生成独立回执。回执绑定当前依赖和授权，当前权限持续重检。
4. 公共 Apply 冻结整个图，审批人读取准确候选并签审。已存在对象仍按当前权限及 expected version 检查。
5. 受控根事务内依次调用三个 Owner 的内部 stage/port；事务绑定签名将子命令与整包批准、输入、核验和实际别名映射关联。
6. 新对象 UUID、正式核验事实、配对权限转换、子命令来源、outcome 与成功审计一起提交；任一步失败一起回滚。

数据库写入不信任会话变量本身。签名验证涵盖域、数据库事务、执行人、准确候选和命令；提交成功 outcome 前再次核对完整子命令集合及返回事实。原手工签名不能用于工作簿，工作簿签名不能用于其他域或事务。

预授权转换按本命令的准确端点和允许动作计算，并与该人员当前创建策略取交集。一个配对的 READ 不授予另一个配对的端点权限，也不扩大为 WRITE/REVIEW。接收时用同一有界解析器证明全部实际行均有准确清单坐标；证明成立后，受限文件读取按实际数据集与治理范围逐项核权。遗漏行或结构拒绝时仍保留原件，但采用三个数据集与声明/接收范围的保守保护维度。不能只靠 ORG01 锚点权限；完整映射的合法输入不要求无关的数据集与范围组合。

已存在端点和范围使用同一 Owner 的只读准入；混合的新旧范围按每项服务计算相邻期间覆盖，新主体/院区使用已声明的资料期间，所有新身份仍等待数据库签发。审批后的相关依据失效返回 stale；应用时继续执行共享写入准入和约束。

## 回执与限制

同请求重放返回同一事实集合；响应送达状态不属于事实身份。恢复已提交结果按当前对象 READ 授权，无需旧材料重新有效或再次取得解密密钥。候选依赖变动时不能自动重算并复用审批；新 revision 重新进行核验与授权。

源 DRAFT 或不支持的生命周期声明保留并阻断。新院区只创建为筹建；关系存在不表示运行或医疗许可合格。FULL、其他组织文件格式、批量生命周期、真实医院接入和维护页面保持本票范围外。UI、实际服务重启、正式验收为 NOT_RUN。

## PR #17 追加审阅修复

原两项意见及随后新增的适配器发现均在同一 PR 内处理，不进入下一阶段。

- `0070_organization_bundle_pair_policy.sql` 前向替换配对授权转换函数，0001–0069 原文件不变。预授权与当前有效身份、动作权限和新端点创建策略相交；已有端点要求精确 READ，不因关联操作额外要求端点 WRITE。REVIEW 不自动获得创建策略未允许的 READ_RESTRICTED。无权限的旁观受授权人被过滤，不影响有权提交者的合法整包事务。
- 该迁移只约束后续转换，不自动删除已经保存的人工或历史授权。是否对持久库部署及审核旧授权需单独记录，不能把临时库通过称为持久环境已经修复。
- 解析错误采用实际工作表/CSV物理行，成功规范单元格仍同时保存逻辑 `row` 和物理 `sourceRow`。错误工作簿按 `sourceRow` 取回原值；已有签名解析产物不被原地改写，表头错误仍为物理第1行。

## PR #17 第二轮追加审阅修复：组合解析证据进入通用 Dry-run

组织组合校验保存的是 `STRICT_ORG_BUNDLE_V1` 多工作表受保护包络，不得交给只接受单表 `STRICT_V1/STRICT_V2` 的验证器。共享验证证据读取现在先校验签名、准确 source/job/revision/contract、manifest/contracts digest 及三表结构，再以区分字段返回 flat parse 或 organization bundle。通用质量纠错继续只消费 flat parse；bundle 不被伪装成单表行集。

Dry-run 按锚点数据集从已验证组合证据中选择相应工作表行数，并把完整受保护解析证据纳入观察绑定。它仍只返回带 `BLOCKED_DEPENDENCY` / `INTENT_MAPPING_UNAVAILABLE` 的诊断预览，不绕过组织 Owner 的独立核验、审批与原子 Apply，也不把 READY 适配器等同于业务可执行。

本轮新增真实数据库反例在旧运行时得到 `DRY_RUN_FAILED`，其余32项通过；修复后 fresh 33/33、0064→0070升级 33/33，既有 Dry-run 数据库/单元回归17/17，P0-06质量阶段门禁、parser 56/56、P1-05 unit 6/6及相关 typecheck/build/boundary/layout/diff检查通过。持久库、持久授权和迁移前缀均未变；源码迁移仍为0070。
