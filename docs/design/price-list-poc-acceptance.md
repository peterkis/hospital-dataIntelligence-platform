## 1. 验收目标

价表POC的验收目标不是证明系统已经生产就绪，而是用完全合成的数据证明以下能力形成同一治理闭环：

1. 核心与邻接薄切对象可以通过管理界面和REST API完成受控增、删、改、查。
2. 身份、版本、双时态、完整发布快照、失效和补偿语义可复现。
3. 导入可以批次内判重、原批次幂等重试、新批次进入版本变更，并允许单行失败而保留成功行。
4. 价格、资格、外部绑定、计价规则、组套和医嘱收费解析确定、可解释、失败关闭。
5. 人员与服务身份隔离、显式外部身份绑定、平台本地对象级权限、职责分离、跨域确认、高风险审批和紧急单人暂停可执行。
6. 发布、Outbox、仿真消费、水位、缺口恢复、回执和防篡改审计形成闭环。
7. Phase 01门禁通过后，受控导出可以从固定规范快照为合成仿真消费者生成只含清单和CSV的确定性无压缩ZIP非权威派生制品，区分确定性转换错误与瞬时技术故障，以独立PostgreSQL `bytea`和短事务原子固化成功结果，保证完成制品保留至POC证据基线整体处置、新作业只追加且权限变化不删除，并通过有限完整重建式重试、平台受控取得、交接、回执、对账和检查点完成闭环；高风险语义转换、真实厂商和逐记录推送不在本次验收范围。

任一强制场景失败即阻断验收，不能用总体通过率、其他场景成功或人工说明抵消。

## 2. 验收边界

### 2.1 纳入验收

- 核心对象完整实现。
- 已确认的邻接对象少量样本，但每类样本仍验证完整治理生命周期。
- 两个与长期生产消费者使用相同契约的仿真消费者。
- 独立Keycloak验证身份提供方、Fastify人员服务端OIDC会话、两个仿真消费者各自的服务客户端及平台本地授权。
- A01至G12共72个强制场景的自动化REST API验证；A01至F08为既有60项，G01至G12为受控导出新增12项。
- U01至U20共20个管理界面代表性端到端场景；U01至U16为既有16项，U17至U20为受控导出新增4项。
- 全流程审计、请求关联、版本差异和证据导出。
- governance-api深模块公开入口、依赖边界、表所有权、组合根和事务作用域的自动化验证。
- Phase 01门禁通过后的`MANAGED_EXPORT_HANDOFF`邻接薄切，只连接合成仿真消费者并使用默认受控表示转换，由G01至G12及U17至U20验证完整闭环。

### 2.2 不纳入验收

- 真实患者、医嘱、执行、收费、结算或医保待遇事实。
- 真实HIS、财务、体检、历史或院区系统接入。
- 生产Kafka、Debezium、缓存、容量、P95/P99、SLA、灾备或影子计费。
- 全院收费项目、医保目录、临床目录或政策资料的全量覆盖。
- 招标基线、生产上线结论或评级达标声明。
- `RECORD_PUSH`逐记录初始化推送、真实厂商受控导出接入及任何高风险语义转换。

### 3.3 合成身份与职责

测试身份至少覆盖以下职责，实际可由一个合成人员组合多个不冲突角色：

- 收费项目、价格、映射、政策、医保、规则、组套、临床目录和执行服务数据管家。
- 全院价格Owner、各邻接对象唯一Owner和专业复核人。
- 来源领域Owner、集成交付Owner及具备目标消费者和治理对象级权限的受控导出操作员。
- 院区A、B的数据管家和业务确认人。
- 具备对象级`EMERGENCY_SUSPEND`权限的紧急操作者。
- 独立事后复核人和只读审计员。
- 两个最小权限的仿真消费者服务账号。

每个由冻结审批模板要求提交—终审分离的场景必须使用不同主体ID，不能仅在同一账号上切换角色模拟。纯投影Schema升级只有在满足第4节第29项全部限定条件时，才允许同一主体分别执行提交与平台契约终审动作。

上述人员职责使用相互独立的合成Keycloak账号并显式绑定平台人员安全主体；另设一个“同一合成人员绑定第二个外部账号”的负向样例，证明切换账号不能绕过职责分离。两个仿真消费者分别使用不同的机密客户端、客户端凭据和平台服务主体，不得共享人员会话或服务账号。

G01至G12必须在fixture清单中列出其产生或引用的消费者交付配置身份及版本、初始化作业、转换错误、派生制品、交接、回执、对账和检查点对象及摘要；其数量由12个强制场景的正负路径决定，不能用预置成功状态替代真实流程。

## 4. 统一执行条件

1. 平台应用、治理数据库会话、测试运行器和浏览器业务显示均验证`Asia/Shanghai`语义。
2. 所有平台自有业务、记录、审计、调度、消费和界面日期时间使用不带`Z`或UTC偏移的ISO 8601本地日期时间值并固定按`Asia/Shanghai`解释；带偏移输入必须失败，不能剥离偏移后保存。OIDC/JWT标准`NumericDate`只在认证适配器中按数字校验，不进入公开业务字段。
3. 治理Schema只允许`timestamp without time zone`和`tsrange`承载日期时间及其范围，并通过类型清单证明不存在`timestamp with time zone`、`timestamptz`或`tstzrange`。
4. 时间边界按左闭右开`[from,to)`执行。
5. 所有金额和数量使用Decimal，并固定记录精度、舍入模式和舍入层级。
6. 每个API请求携带请求ID；幂等写操作携带幂等键。
7. 所有预期失败必须同时验证HTTP状态、稳定错误码、规则编号和审计结果。
8. 每个发布场景必须验证发布对象、完整快照、Outbox、两个消费者回执和审计关联。
9. 每个解析场景必须验证最终状态以及逐步命中、回退、拒绝或冲突证据。
10. 相同本地日期时间和并发写入场景必须按显式流内序号稳定重放；序号空洞不得修补复用，跨流结果不得声明全局先后。
11. 所有公开API必须由TypeBox Schema生成冻结OpenAPI 3.1契约；管理界面、仿真消费者和契约测试只使用该产物生成的客户端，重生成漂移、平行手写契约、导入后端内部类型或把本地日期时间声明为RFC 3339 `date-time`均视为验收失败。
12. 管理界面必须以React/Vite静态构建由Fastify同源提供，并只通过冻结契约生成客户端访问API；浏览器篡改权限、流程状态、价格结果或审计展示不能改变服务端权威结果，治理写操作在服务端失败时不得显示为已发布、已批准或已暂停。
13. 每个变更请求必须冻结已发布审批模板版本、风险结果、必需阶段和内容摘要；模板升级不得迁移进行中请求，BPMN、任意脚本、非法跳级、超时自动批准或外部流程状态旁路均视为验收失败。
14. Keycloak精确版本及镜像摘要必须进入环境证据；人员登录真实执行Authorization Code、PKCE S256、`state`和`nonce`校验并建立Fastify服务端会话，浏览器不得出现访问或刷新令牌；服务身份使用各自Client Credentials。每个受保护请求必须从显式绑定解析本地安全主体并执行对象、操作、院区和有效期授权，Keycloak角色、名称匹配、服务身份审批、跨账号自审批、Cookie伪造或CSRF旁路均视为验收失败。
15. 发布事务不得调用消费者；同一Fastify/Node进程内的Outbox模块必须在提交后唤醒并能仅依靠数据库轮询从丢失唤醒、进程重启和积压中恢复。认领使用短事务租约和`FOR UPDATE SKIP LOCKED`，网络期间不得持有数据库锁；每个消费者具有独立投递和只追加尝试，崩溃窗口产生的重复投递由`event_id`幂等，一个消费者失败不阻塞另一个消费者，重试耗尽保留事件并生成影响事项。
16. TypeScript测试资产和证据编排是唯一自动化验证权威；Vitest 4.1.6承担通用测试，Playwright Test 1.61.0只承担真实浏览器端到端。Fastify模块及路由测试使用实际应用入口和`inject()`，REST场景只使用冻结OpenAPI生成客户端。
17. Testcontainers必须从空环境启动真实PostgreSQL 18.4、Keycloak 26.7.0和Toxiproxy。事务及崩溃窗口由生产不可启用的枚举化测试故障点验证，网络延迟、超时、断连和依赖重启由代理及容器生命周期验证；SQLite、内存数据库、伪造IAM或预置成功消费者不能进入结论。

40. 容量字段分布按输出字段身份和稳定记录全序精确执行，禁止运行时随机近似。`N10`、`N30`、`N50`和`N100`中每个可选输出字段必须恰有70%记录有值、30%记录使用冻结空值表示；每个适用的非空变长文本字段分别恰有70%短值、25%中值和5%长值，目标Unicode码点长度为冻结合法最大长度的20%、50%和85%，取整、最小值及合法边界夹取由画像版本冻结。普通画像只用不含CSV结构字符的安全单字节基线字符；身份、代码、枚举、引用、摘要和严格模式字符串使用各自合法确定性生成器且不进入文本长度分布。`W50`所有可选字段均有值，变长字符串目标为合法最大长度的90%，唯一性后缀必须包含在长度预算内，非字符串采用最长合法序列化值，字符串仍只用单字节字符。`E50`逐字段复用`N50`相同的70%/30%和Unicode码点短中长分布；每个适用文本字段的非空单元格必须按稳定记录顺序恰分为五组各20%：纯中文、中文与ASCII混合、中文混合且含逗号、中文混合且含双引号、中文混合且含逗号/双引号/LF。适用性必须按冻结输出列身份显式列举，只允许Schema容许的自由或展示文本，LF只进入容许多行的字段；身份、代码、枚举、引用、摘要、金额、数值、日期、日期时间、布尔和不兼容模式字段必须排除。任一E50类别无合法字段、映射与Schema不一致、静默跳过或重分配均使画像冻结失败。字符串长度按OpenAPI 3.1/JSON Schema Unicode码点解释；容量结论仍只按最终确定性ZIP精确字节计量。`F00`不承担该容量分布推断。

由于每个`E50`适用字段必须完整形成五组，不允许LF的单行文本字段整体排除在五组压力清单之外并保持普通内容，不能只执行前四组或把第五组转移到其他字段。

## 5. 72个强制REST场景

以下七组共计72个强制REST场景。A01至F08共60个既有场景保持原编号、分组和口径，G01至G12为`MANAGED_EXPORT_HANDOFF`新增场景；不得改名、替换、抵扣或合并计数。

一个编号可以包含明确列出的参数化子用例；只要任一必需子用例失败，该编号即失败。A07、A08和A12必须至少对收费项目、价表、外部代码、政策适用认定、医保映射、资格规则、计价规则、收费组套及医嘱收费规则各选一个代表对象执行，不能只用收费项目证明所有对象都具备治理生命周期。

### A组：导入、CRUD与版本，共12项

| ID | 场景 | 必须满足的预期结果 |
|---|---|---|
| A01 | 混合批次导入 | 同一批包含正确行和错误行；正确行形成草稿，错误行保留字段级错误，批次为`PARTIAL_SUCCESS`，正确行不回滚。 |
| A02 | 批次内同键同内容 | 首个候选正常处理，其余行标记`DUPLICATE_IDENTICAL`并忽略，不生成重复身份或版本。 |
| A03 | 批次内同键不同内容 | 所有冲突行标记`DUPLICATE_CONFLICT`，不以文件顺序或最后一行决定内容。 |
| A04 | 原批次幂等重试 | 修正失败条件后使用原批次ID重试；已成功行被跳过，失败行重新处理，不产生重复版本。 |
| A05 | 新批次同业务键 | 变更内容在新批次导入时进入版本变更候选，不覆盖已发布版本，也不作为重复静默忽略。 |
| A06 | 界面与API导入同规则 | 同一文件经管理界面和REST API进入相同服务，行状态、错误码、规则版本和结果计数一致。 |

| A09 | 非实质变化沿用身份 | 收费项目改名或说明完善创建同一稳定身份的新版本，历史名称和引用版本可查询。 |

| A11 | 未来生效版本 | 发布未来业务时间版本；生效前解析旧版本，到达边界后解析新版本，调度与界面均按`Asia/Shanghai`。 |

### B组：时间、院区与价格解析，共12项

| ID | 场景 | 必须满足的预期结果 |
|---|---|---|

## 6. REST API全覆盖要求

### 6.1 覆盖定义

“API全覆盖”表示A01至G12每一个场景都有可重复执行的自动化REST测试，而不是仅验证接口存在或只覆盖成功路径。每项测试必须：

1. 通过公开治理服务API准备或引用fixture，不直接写业务数据库制造结果。
2. 验证请求、响应、错误码、状态变化、版本和内容摘要。
3. 通过审计、证据、快照、Outbox或消费者回执API核对副作用。
4. 清楚标记所覆盖的场景ID和规则编号。
5. 可以单独执行，也可以按固定顺序执行完整验收套件。

这些场景统一由Vitest运行，并通过冻结OpenAPI生成客户端访问真实Fastify服务及Testcontainers依赖；Fastify `inject()`只用于更低层的模块和路由验证，不能替代完整REST场景。

20. 两个消费者的精确订阅支持声明、发布前预检、不兼容隔离和升级后受控重放全部通过；`UNSUPPORTED`不回滚发布但只阻断对应投递，无网络、尝试和水位推进，兼容消费者继续，原事件、快照、预检及影响事项不被覆盖，且不存在自动降级、转换或迁移。
