# P1-06 review repair: required migrations and partial endpoint authority

This note extends ADR 0127. It does not authorize a production deployment or mark formal acceptance complete.

## Release and deployment boundary

`tooling/vnext/workspace-migrations.mjs` is the shared release boundary. The current release ends at `0074_workspace_partial_endpoint_authorization`. The real ordered migration IDs and SHA256 values are checked with the existing lineage `checkPrefix`; the number of ledger rows alone is not sufficient. A truncated or unexpectedly extended release manifest fails closed.

Persistent workbench startup inspects the receipt-owned database once, before opening a service connection, loading installed organization keys, constructing any Owner or listening. A pre-workspace prefix below 0071 retains the existing catalog-only behavior. A database with workspace storage at 0071, 0072 or 0073 is refused with `WORKSPACE_MIGRATION_REQUIRED`. It must be upgraded through the required release before workspace routes can run. Startup does not silently migrate a persistent database.

`prepareWorkspaceDeployment` accepts supported exact prefixes from the P1-05 baseline 0070 through the current release. Normal deployment migrates all remaining files in order and verifies the complete returned ledger before granting workspace functions or producing PASS evidence. `reuseExisting` requires the complete current prefix; it cannot be used as an upgrade shortcut. Existing receipt identity, role OID, predecessor rows, key bytes, type verification and completion-preservation checks remain in force.

Any future SQL change must advance this one release boundary and its tests. Never repair a lineage mismatch by rewriting an applied ledger, changing a checksum or resetting the database.

## Partial ORG03 editing drafts

The forward-only 0074 migration preserves migrations 0071–0073 and every stored draft. It replaces only the existing authorization function, retaining its OID, owner and ACL. A baseline-text mismatch aborts the migration rather than guessing at an unknown function definition.

For an incomplete ORG03 pair, each selected subject or campus must exist in its proper owner table and remain readable by the actor under the endpoint's actual scope. Unknown or wrong-kind UUIDs are not creation-policy NIL references. The existing scope-level creation/edit/read-restricted permissions still apply to the incomplete draft. Once both endpoints are selected, the existing exact-pair `operating_authorize` rule applies, including endpoint READ and the pair-specific operation/READ_RESTRICTED grants. This repair does not impose endpoint WRITE in place of relation/pair authority.

The shared function is called by draft restore, list, capabilities, save and submission. When saving an existing draft, authorization of its previous metadata also checks its selected endpoint, preventing a revoked endpoint from being erased to escape the check. Read denial happens in SQL before the encrypted envelope is returned for decryption. Restoring the relevant grant permits the same unchanged sealed draft to be read again.

## Verification scope

- `p1-06-migration-gates.test.ts` exercises the actual startup and deployment orchestration functions against controlled platform boundaries. Its WSL transport, installed secrets, service owners and type-process result are doubles; these tests are not evidence of a real persistent/WSL deployment.
- `p1-06-partial-endpoint-db.test.ts` runs real Owners, HTTP, encryption and SQL for both ESTABLISH/VERIFY_SCOPE and subject-only/campus-only drafts. It checks continued NIL permission, endpoint revocation, reads/list/capabilities/save/clear/submit denial, unchanged drafts and no command side effects, restored access, complete-pair denial and independent approval/Apply success.
- With `HDIP_REVIEW_CI_ENDPOINT_UPGRADE=1`, the isolated CI suite first runs at 0073, reproduces four HTTP reads, four SQL reads and four resaves after endpoint READ revocation, then upgrades the same populated database to 0074 and repeats the denial checks. The adapter checks database identity, the 73 existing ledger entries, all prior data tables, and affected function OIDs/owners/ACLs.
- Existing unit, fresh database, browser races and 0071→0072 / 0072→0073 regressions must also pass on the exact final commit. No runtime grant or input schema is weakened to make tests pass.

Actual receipt-owned WSL deployment, installed-key rotation, production deployment, full-site manual acceptance and formal acceptance remain separate, unexecuted activities in a GitHub-only review repair.
