# P1-06 review repair: exact workbook manifest references

## Authenticated format boundary

Private workbook drafts are authorization-bearing encrypted records. Dataset contracts, governance scopes and `manifestProtected` alone do not identify exact objects carried by rows. New V4 bundle metadata includes a deterministic `manifestReferences` projection for each row target and each ORG03 platform subject/campus endpoint: row, dataset, scope, intent and expected versions. Alias-only rows produce an authenticated empty reference set.

V1, V2 and V3 retain their original projection byte-for-byte. V4 is detected by the presence of `manifestReferences`; it must not be retroactively added to V3 authentication. The existing content digest and canonical projection comparison bind references to the encrypted draft. Metadata cannot omit references without failing authentication when plaintext is read. Workbook bytes need not be present for retained manifest references to require authorization.

## Current permissions

Migration 0077 extends the shared `workspace_authorize` after existing bundle-dimension checks. ORG01 and ORG02 row targets require the requested permission on the actual object and scope. ORG03 relation targets require the real relation pair, each platform endpoint requires current READ in its own actual scope, and a complete platform pair requires the corresponding current permission. WRITE maps to ESTABLISH or REVISE according to row intent; relation targets always retain revision semantics. Cross-scope endpoints are not equated to the receiving scope.

The function is used by read, list, capabilities, save, discard and submit. The existing previous-metadata READ/READ_RESTRICTED/WRITE checks remain effective: clearing or retargeting a draft cannot evade a permission revoked on its saved revision. A WRITE-only revocation does not unnecessarily prohibit otherwise authorized reads. No new user grants are introduced.

## Legacy and deployment limits

Old protected bundle metadata without authenticated exact references is withheld before its encrypted envelope is returned. Such revisions stay immutable audit records and must be recreated from an authorized source; this repair does not claim transparent recovery of every legacy workbook. ACCESS_DENIED allows list filtering to hide those entries without poisoning the entire draft list. Safe empty V3 workbooks can still be read and explicitly saved in V4. The stricter 0076 guard for ambiguous payload-free V1/V2 revisions is preserved, not replaced or bypassed.

Migrations 0071 through 0076 and stored ciphertext/digests/history are unchanged. The failed, uninstalled 0077 candidate is corrected before deployment; the migration runner applies it transactionally. Runtime and deployment share the required 0077 ID/checksum prefix. No automatic persistent-database upgrade occurs at application startup.

## Repeatable verification

`p1-06-manifest-reference.test.ts` checks exact projections, historical format compatibility, byte-free references and non-mutation. Full startup/deployment orchestration tests are retained rather than replaced by helper-only assertions.

`p1-06-manifest-reference-db.test.ts` uses actual HTTP and PostgreSQL. Its permission matrix covers ORG01, ORG02, complete ORG03 pairs, relation targets and partial endpoints. READ, READ_RESTRICTED and mutation-only revocations are distinguished. Tests assert permitted replacement capabilities, denied resave/retarget/submit/discard operations, no stored-state side effects, grant restoration and idempotent save. Additional cases cover cross-scope endpoints, a deliberately corrupted metadata/ciphertext binding, and independent workbook approval with COMMITTED Apply and replay.

The separate populated 0076-to-0077 run first reproduces old HTTP reads, SQL envelope reads and SQL resaves under revoked exact grants, then upgrades the same database. It compares the 76 old ledger entries and hashes, all preexisting table data summaries, database identity and relevant function OIDs/owners/ACLs. Legacy filtering and empty-V3 recovery are tested after upgrade. Provisioning does not rename tracked migrations.

Both CI workflows retain exact HEAD and machine-readable results. Final pass/fail status is the recorded workflow/artifact result, not a claim in this document. These runs use isolated GitHub-hosted synthetic databases; actual persistent deployment, production and full-site manual acceptance remain outside this repair.
