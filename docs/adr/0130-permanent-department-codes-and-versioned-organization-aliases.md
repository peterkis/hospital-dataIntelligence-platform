# 0130: Permanent Department code ownership and versioned organization aliases

Status: Accepted for synthetic CORE development (2026-10-01)

## Context

P2-01 retained `department.code` as the initial registration evidence. P2-04 must support recoding without changing the Department stable ID, while ORG23 includes aliases and source codes with different identity semantics. The user confirmed permanent code ownership, whole revision atomicity, the preferred alias bucket and separate end/retract operations.

## Decision

Official Department code ownership is permanent within `SYNTHETIC_DEPARTMENT_CODE`. An ended or retracted code cannot move to another Department or revive on its original Department. A code change ends the old interval and registers a new code in one root transaction; it preserves the stable ID. The initial ORG04 code remains evidence. ORG04 creation and ORG23 share the same reservation and lock protocol, and Department readers expose `initialCode`, `effectiveCode`, `codeVersion` and `codeEvidence`.

Business intervals use Asia/Shanghai local strings, microsecond precision and `[from,to)`. Platform R is generated by the database; source `recorded_at` is separate evidence. Readers select the latest complete version at R before testing B. End only shortens a period. Retract removes the assertion from new R while old R retains the original. Neither operation falls back to a prior open version.

Aliases bind one target, kind and scheme permanently. Correction appends a full value/language/preferred/period version. Aliases may repeat across targets. The preferred bucket is target type + target ID + kind + scheme + exact language; empty language is its own bucket. At most one preferred assertion overlaps in a bucket. An explicit atomic handover is required. Search codes and names never resolve platform identity.

CORE aliases support LEGAL/CAMPUS/ORG via public target Owner ports. Official codes support ORG only. Institution identifiers and Campus codes remain with their original Owners. SOURCE_CODE remains a blocked ORG23 input with an explicit ORG22 handoff; no context inference or cross Owner write is introduced. FULL and unimplemented targets stay blocked.

The finite scheme policies bind kind, target types and synthetic issuer. A published ORG23 contract supplies adopted code sets and their validity; independent personnel verification and platform candidate approval are both required. This does not constitute hospital policy adoption. Each revision is atomic, with at most 100 expanded domain commands; CHANGE counts as two.

## Consequences

Migration 0115 adds append-only relationships and versions. Migration 0116 integrates contract/parser policy and ORG04 reservation/read behavior. Installed predecessor migrations, facts and approvals remain unchanged. Migration-created facts use actual R; reads before the migration derive code evidence from the original ORG04 version instead of inventing a historical identifier version.

The API response change requires current client regeneration. Historical hierarchy snapshots and source mapping targets retain their pinned identity/version facts. UI maintenance belongs to P2-07; FULL/P2-08 and formal acceptance are separate. See [P2-04 design](../design/p2-04-organization-identifiers.md).
