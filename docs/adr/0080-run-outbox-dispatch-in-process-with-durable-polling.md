# Outbox使用同进程派发与持久化轮询

Phase 01把Outbox派发器建设为模块化单体同一Fastify/Node进程内的后台基础设施模块，不建立独立Worker部署、数据库触发器、`LISTEN/NOTIFY`、CDC或外部消息中间件。发布事务只原子登记发布、快照、审计和不可变Outbox事件，不执行网络调用；提交成功后以进程内信号缩短等待，并始终以数据库周期轮询作为丢失唤醒、进程重启和积压恢复的可靠来源。派发器在短事务中使用租约及`FOR UPDATE SKIP LOCKED`认领按消费者独立的投递记录，提交认领事务后才在事务外执行至少一次网络投递，再以新事务写入只追加尝试和投递状态；进程在消费者成功后、结果落库前崩溃时允许重复投递，由消费者以`event_id`幂等。每个消费者分别维护事件投递、重试、顺序阻断和回执，一个消费者失败不得阻塞另一个消费者或回滚平台发布；重试耗尽后事件不得丢弃，必须保留并形成待人工处置的影响事项。投递顺序仍由对象版本和尝试序号决定，租约时间及`next_attempt_at`只负责调度，不取得顺序主权。

ADR-0086进一步确认：上述后台派发器是`release-distribution`深模块的内部状态机，不是独立`outbox`或`delivery`模块；发布登记和提交后投递共享一个模块所有权与逻辑接口，但继续使用彼此隔离的事务阶段。

[ADR-0089](0089-use-exact-consumer-projection-support-and-isolated-delivery-blocking.md)进一步区分网络失败与契约不兼容：不兼容投递在认领前即被隔离，不产生发送尝试或水位推进，也不回滚领域发布或阻断其他消费者。
