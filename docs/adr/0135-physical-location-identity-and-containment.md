# 物理地点身份与包含关系独立治理

用户批准 P3-06 将物理空间交给唯一 location-master Owner，不复用行政
Department/GROUP 身份。每院区在同一 B/R 最多一个有效 CAMPUS 地点根，
该根引用院区稳定身份而拥有自己的 DB 生成地点 ID。楼宇、楼层、房间类和
窗口采用严格包含矩阵；OTHER 未有明确分类依据时保留候选但阻断发布。
这是 TEST POLICY ONLY 合成采纳，不宣称实际后勤政策已经批准。

地点代码在院区内永久保留原地点归属，改码不能释放历史代码。房间号和
显示名是版本事实，改名、重新编号和包含关系调整保持同一物理空间身份。
创建输入 alias 不是平台 UUID；同一 job/revision 内明确解析，既有地点用
typed reference 和期待版本。跨院区移动在本票拒绝。

属性和父关系采用同一 R 下最新适用局部断言，整段分割校验单父、无环、
类型和院区一致。永久关闭从批准业务边界持续遮蔽所有后来生效的开放断言，
旧 R 仍可复现原认知。关闭不得改变属性、扩张期间或复活身份。

院区资料须覆盖新增/扩张完整期间；筹建与暂停允许物理地点维护，院区
永久退出后的扩张被阻断，物理有效不授予运营或临床许可。关闭沿用既有
接受证据并保留当前授权、准确版本、独立审批，避免上游失效阻止收尾。
非叶子退出显式处置全部未来后代；房间拆分原子关闭前驱并创建至少两个
不同新 ID，冻结前后关联。同院区、同楼层拆分与树内处置不代表组织使用
关系、人员、床位或消费者已经完成跨域迁移。

按已批准的房间类定义，ROOM、CLINIC_ROOM、OPERATING_ROOM 和 WAREHOUSE
均可作为物理空间拆分的前驱或后继。WAREHOUSE 在这里仅代表楼层内物理
空间；拆分不移动库存、不产生仓储业务身份或资源占用处置。

沿用公共保护输入、审批、原子 apply/outcome 和审计。所有 writer 共享现有
治理事务锁，有限 SQL 命令以事务绑定签名认证，再独立校验最终图。
代价是合成开发阶段的保守串行化和整个院区树的审批依赖绑定；没有当前
瓶颈时不建设额外调度、图数据库、锁框架或消息平台。
