# 接口与同步规范

## 1. 四类交换方式

1. **REST/API**：在线查询、注册校验、申请与管理；禁止同步接口直接完成高风险患者合并。
2. **FHIR R4**：Patient、Organization、Practitioner、PractitionerRole、Location、Medication、Device、CodeSystem、ValueSet、ConceptMap等互操作资源；院内模型不能被FHIR资源边界反向绑死。
3. **Kafka事件**：主数据变更、合并、停用、标准发布和质量告警；事件只携最小必要字段，敏感详情通过受控API获取。
4. **批量文件/对象**：历史回灌、全量快照、厂商批量交换；必须有manifest、记录数、checksum、模式版本和重传机制。

## 2. 通用协议

- TLS 1.2+，内部关键链路mTLS；服务账号单独申请、最小权限、定期轮换。
- OAuth2/OIDC scope控制能力，OPA按主体、角色、用途、数据域、字段、院区、时间、环境决策。
- 所有写接口要求`Idempotency-Key`；返回`traceId`、业务请求号和版本。
- 乐观锁使用`ETag/If-Match`或`expectedVersion`，防止静默覆盖。
- 时间统一ISO 8601并明确时区；金额、计量单位、状态和值域不得用自由文本。
- 错误结构：`code/message/traceId/details/retryable`；禁止在错误消息中回显证件、病历正文和密钥。

## 3. 事件可靠性

- Kafka：生产关键Topic副本3、`min.insync.replicas=2`、`acks=all`。
- 同一业务对象使用稳定Key保证对象内顺序；不得假设跨Key全局顺序。
- 生产者采用事务性Outbox；消费者采用Inbox/业务唯一约束实现幂等。
- Schema兼容默认`BACKWARD_TRANSITIVE`，删除字段先弃用、后移除；破坏性变化升主版本Topic。
- 有限重试后进入DLQ并创建工单；DLQ必须有Owner、处置时限和重放审计。
- 患者合并、药品停用、人员离职等事件要求消费确认、影响清单和高优先级告警。

## 4. 性能目标参考

- 主数据查询：P95 ≤ 500ms，5xx < 0.1%。
- 患者候选匹配：P95 ≤ 800ms；超时可进入人工/异步流程，急诊不得因平台不可用而拒绝救治。
- 关键变更：核心消费者5分钟内消费并确认；普通参考数据10分钟内同步。
- API峰值按3000 QPS、CDC短时峰值3万条/秒设计，生产采购前必须真实压测。

## 5. 降级原则

- 急诊/门诊注册：MDM不可用时签发受控临时标识，恢复后补匹配；不得用旧数据盲目自动合并。
- 组织/药品等查询：允许读取带版本与过期时间的本地缓存；停用类高风险事件设置短TTL和强制失效。
- 临床报告、医嘱、检验结果：源业务系统始终是原始事实权威；治理平台只读整合，不能反向覆盖原报告正文。
